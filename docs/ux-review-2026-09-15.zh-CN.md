## P1-1 全屏时 toast、重连提示条与横幅不可见（实测确认）

**现象**：播放器全屏（原生 Fullscreen API）后，房间里的进出提示、播放/暂停提示、错误与撤销
toast 全部看不见。退出全屏后才一次性看到残留的提示或直接错过。网络重连提示条与
投票/恢复队列横幅同样在画面之外。

**实测证据（2026-09-15）**：

1. 会话 A 播放中进入全屏，`document.fullscreenElement` = `.video-subcontainer.player-fullscreen`。
2. 会话 B 重新进入房间，会话 A 的轮询记录到真实 toast：
   `{"items":["偷吃零食的椰子 加入了房间"],"insideFs":false,"z":"1000"}`（多次采样一致）。
3. 结构判定：`document.fullscreenElement.contains(document.querySelector(".toast-list")) === false`。

**根因**：

- `client/src/components/Notifier.vue:33-42`：`.toast-list` 是 `position: fixed; z-index: 1000`，
  挂在 `.v-application__wrap` 下，**不在全屏容器子树内**。原生全屏只渲染全屏元素（顶层
  top layer），子树之外的节点一律不可见。
- 网页内全屏降级路径同样失效：`client/src/views/Room.vue:1674-1677`
  `.video-subcontainer.player-fullscreen { z-index: 3000 }` > toast 的 1000。
- 同一原因影响画面外的其它组件：网络重连提示条（`RoomConnectionNotice`，`Room.vue:45`，
  在视频区上方）与投票/恢复队列横幅（`.banners`，`Room.vue:268-271`）。

### 决策：不做「纯净模式」，做三档「全屏提示」偏好（默认仅重要）

**关键事实（决定方案的三条）**：

1. 全屏容器 `.video-subcontainer`（`Room.vue:46-219`）内**已有完整的必要信息通道**：
   播放器错误卡（`OmniPlayer.vue:34-58` 的 `.playback-error`）、加载/缓冲提示、缓冲门、
   语音条。→ 全屏少弹提示**不等于**用户会陷入「黑屏且没有解释」。
2. 断线时会自动退出全屏：`Room.vue:945-950` 对 `showDisconnectedOverlay` 的 watch 调用
   `fullscreen.exit()`，因此断线覆盖层不会漏。
3. 真正漏在容器外的只有三类：toast、重连提示条、投票/恢复横幅——它们要在**同一批改动**里处理。

**为什么不做单独的「纯净模式」**：现有设置已经是按类别控制提示
（`presenceNoticeSeconds` / `seekNoticeSeconds`，0 即关闭，`VideoSettings.vue:533-534`），
再引入一个「模式」会与之重复并互相冲突（例如用户已经把「用户进出提醒」设为关闭，
「纯净模式」就没有额外含义）。把它做成同列的第三个偏好，理解与维护成本最低。

**为什么不默认「全部显示」**：房间事件里最吵的三类是添加/移除/跳过，时长 **20 秒**
（`stores/events.ts:32,62,72`），多人房里会持续遮挡画面；日志/实测中都出现过同一分钟
内多条此类提示。

**分级（按后果分级，而不是按组件分级）**：

| 级别 | 内容 | 全屏默认 | 备注 |
| --- | --- | --- | --- |
| critical | 播放错误与可重试失败、需要动作的撤销窗口、会导致本机跳转的房间操作（跳过 / 跳进度）、被踢 / 房间结束 | 显示 | 不显示会让用户对画面里发生的事失去解释 |
| content | 换片、别人播放 / 暂停 | 显示（弱化，≤ 3 秒） | 与正在看的内容直接相关 |
| social | 进出房间、谁加了 / 移除了什么、链接已复制、聊天浮层 | 抑制 | 其中「加了什么」现在是 20 秒；聊天浮层另有独立开关 |

**三档策略（新增偏好 `fullscreenNoticePolicy`，与 `presenceNoticeSeconds` 放在同一列）**：

- `important`（**默认**）：只显示 critical 与 content；social 一律抑制；
  已有的 `presenceNoticeSeconds` / `seekNoticeSeconds = 0`（关闭）继续生效，不重复设置。
- `all`：全屏与窗口模式一致，显示全部提示。
- `off`（即「纯净模式」）：全屏不显示任何非阻塞提示；错误仍走播放器错误卡，
  断线仍会自动退出全屏。

**全屏内的呈现规范**（与既有「浮层不挡画面、不暂停播放、只有自己的按钮可点」的约定一致）：

- 位置右下角，宽度 ≤ 320px，半透明底，字号 12–13px；
- `pointer-events: none`，仅关闭 / 撤销 / 重试按钮可点；
- 自动消失时长上限 5 秒（把 20 秒的社交类提示压短或直接抑制）；
- 最多同时堆叠 2 条，超出合并计数（例如「3 条新提示」）；
- 不遮挡控制条与字幕区（避让 `--player-controls-height`）。

**实施步骤（本次只记录方案，不动代码）**：

1. **可见性（必修）**：让 `Notifier` 支持 Teleport 进 `.video-subcontainer`
   （`App.vue` 挂载点 + `Room.vue` 暴露容器 DOM 引用，`store.state.fullscreen` 作为触发条件）；
   同批把 `RoomConnectionNotice` 与 `.banners` 在全屏时改由容器内呈现；补一组「全屏内」样式。
   兜底方案（仅覆盖网页内全屏）：把 `.toast-list` 的层级提到 3000 以上（`Notifier.vue:42`）。
2. **分级过滤（无新增 UI）**：给 `toast.add` 增加 `level`（默认 `social`，`critical` 显式标注），
   调用点约 15–20 处，集中在 `stores/events.ts`、`components/players/*`、`AddPreview.vue`、
   `ShareInvite.vue`；按 `fullscreenNoticePolicy` 过滤。
3. **设置项（可选，等真实反馈再做）**：`fullscreenNoticePolicy` 三档开关，
   放进 `ClientSettingsDialog` 与 `VideoSettings` 的「观看偏好」两处，
   并在 `settings.ts` 增加取值校验（沿用 `presenceNoticeSeconds` 的写法，`settings.ts:144-151`）。
4. **文档同步**：`docs/player-interactions.zh-CN.md` 增加「全屏提示」一节
   （默认仅重要、三档含义、纯净模式仍保留错误卡）。

**明确不做的**：不新增独立「模式」概念；不改变窗口模式下的现有提示行为；
不为社交类提示新增设置项（进出已由 `presenceNoticeSeconds` 覆盖，其余保持抑制）。

**验证**：

- 双会话：A 全屏看片，B 反复进出 / 加片 / 跳过 → A 只看到「跳过」这类内容变化提示；
  播放失败与重试按钮在 A 的全屏中可见且可点。
- 三档切换：`all` 时全屏与窗口一致；`off` 时全屏无提示但错误卡照常；切换无需刷新。
- 断网与被踢：全屏下断网能看到重连提示（或明确为「退出全屏后可见」）；
  被踢自动退出全屏后能看到覆盖层。
- 不回归：窗口模式提示的位置与点击行为不变；`prefers-reduced-motion` 下动画仍禁用。

## P1-2 直链元数据在服务端探测失败（实测确认）

**现象**：添加一个常见的海外直链（`https://vjs.zencdn.net/v/oceans.mp4`）时，服务端
`ffprobe` 连不上源站，视频的标题、时长、封面、MIME 全部缺失；卡片上的 47 秒时长实际来自
客户端自己加载视频测得。房间的「自动下一集」按 `length` 判断，缺失或不准时会提前/延后切集。

**实测证据（服务端容器日志）**：

```text
infoextract warn  MISSING INFO for direct:https://vjs.zencdn.net/v/oceans.mp4: title,description,thumbnail,length,mime
infoextract error Failed to get video info for direct:https://vjs.zencdn.net/v/oceans.mp4:
  ffprobe exit code 1 ... Connection to tcp://vjs.zencdn.net:443 failed: Operation timed out
clientmanager error Failed to process client (id=..., room=...) message (action=req): FfprobeError ...
```

- 同一条链接在**客户端**加载正常（`readyState 4`、`duration 46.61`、可播放）——说明是
  服务端出口（腾讯云→海外 CDN）不通，不是链接无效。
- 上一轮的 P0-1（探测失败踢人）已修好：本次日志出现 `FfprobeError` 后页面未断线。

**根因**：

- `server/services/direct.ts` 的 `fetchVideoInfo` 依赖 `ffprobe` 取 `length/width/height/mime`；
  `server/ffprobe.ts:270-292`（`RunFfprobe`）直连 URL 探测，从国内出口访问海外源必然容易超时
  （`-rw_timeout 12000000`，硬超时 35 秒）。
- `direct/hls/dash` 的 `isCacheSafe` 均为 `false`（`server/services/direct.ts:64` 等），
  失败结果也不缓存，每次添加/探测都重跑一遍；「同系列探测」会把这个代价再放大数倍。
- 自动连播判断依赖 `length`：`server/room.ts:915-931`（`realPlaybackPosition > endAt ?? length`）。
  HLS 的时长还是用**最低码率**子播放列表估算（`server/services/hls.ts:87-110`）。

**修复方案（分三步，先做 1 与 2）**：

1. **客户端兜底补全**：视频在客户端 `loadedmetadata` 后回填缺失字段。加一个轻量上报
   （复用 `roomapi` 的 `req` 通道或新增 `POST /api/room/:name/video-meta`），只允许补
   `length/width/height`，服务端校验数值合理（> 0、有限）后写入 `currentSource`/队列项。
   实现位置：`client/src/components/players/OmniPlayer.vue` 的 `onReady`/`loadedmetadata`、
   `server/room.ts` 增加对应处理函数。
2. **失败短缓存 + 探测预算**：把 direct/hls/dash 的探测结果（含失败）写入 Redis/DB，键为 URL、
   TTL 30–60 分钟；`FFPROBE_STRATEGY=run` 增加每主机并发 1–2、全局并发 2–3 的闸门，
   超限直接返回可重试文案，避免慢源拖垮 1 CPU 的容器。
3. **文案与状态**：`infoextract` 的 `MISSING INFO` 属于正常降级，前端卡片已在缺失时不显示
   时长/封面；补一行「时长由本机测得」的说明（可选）并在 `docs/media-parsing.zh-CN.md`
   记录该降级路径。

**验证**：

- 用本次的 oceans 链接在房间内重新添加：卡片先显示占位，客户端播放后时长/分辨率补全；
  服务端日志不再重复出现同一 URL 的 `MISSING INFO`（命中失败缓存）。
- 用一个必然超时的地址（防火墙 REJECT 的端口）连续添加 5 次，容器 CPU 不被占满，
  客户端在 45 秒内得到可重试文案。

## P1-3 无 CORS 源：HLS/DASH 无回退，增强层无守卫（实测 + 代码）

**现象**：源站不返回 `Access-Control-Allow-Origin` 时，只有直链 MP4 有回退；HLS/DASH 直接
失败。另外，画质增强层在无 CORS 源上仍可被选中并挂载 canvas，画面可能被污染成黑屏。

**实测证据（2026-09-15）**：

- 直链回退生效：添加 `https://media.w3.org/2010/05/sintel/trailer.mp4`（无 ACAO 头）后，
  video 元素 `crossOrigin === null`、`readyState 4`、`error === null`，可正常播放
  （对比 9/13 审查中的 P0-2：同一链接当时直接 code 4 失败）。
- 增强层未收口：同一（无 CORS）源上打开播放器设置 → 画质增强 → 清晰化（锐化放大），
  DOM 出现 `canvas.upscale-canvas`（984×410），视频继续播放。

**根因**：

- 直链的回退是**试错式**：线上版本 `main` 的 `client/src/components/players/DirectPlayer.vue:489-499`
  在遇到 `unsupported` 媒体错误后才 `crossoriginEnabled = false` 并 `recovery.retry()`，
  成功后再补一条中性提示（`:424-428`）。也就是**第一次加载必然失败一次**，用户会看到一次
  停顿或错误闪现。工作区分支已新增 `util/cors-memory.ts` 与服务端 `services/cors-probe.ts`
  （`probeCors` 把 `cors` 写进元数据），但**尚未覆盖所有入口**。
- HLS/DASH 完全没有这条路：`HlsPlayer.vue:8` 与 `DashPlayer.vue:9` 硬编码
  `crossorigin="anonymous"`，且 `upscaleMode` 直接取用户设置
  （工作区 `HlsPlayer.vue:72`、`DashPlayer.vue:65`；线上版本同构），没有
  `sourceAllowsCors` 判断，也没有失败回退。
- 增强层的守卫只在 `DirectPlayer` 里（`DirectPlayer.vue:104-106`：
  `crossoriginEnabled ? settings.upscaleMode : "off"`），且是**事后**的：只有在 `crossoriginEnabled`
  被置 false 之后才关。HLS/DASH 连这个都没有。

**修复方案**：

1. **统一能力判定（前置）**：把「该源是否允许跨域」抽成单一函数
   （`util/cors-memory.ts` 的 `rememberedCors` + 服务端元数据 `video.cors`），
   在播放器挂载前决定 `crossorigin` 与增强层可用性。Direct/HLS/DASH 三个播放器共用。
   服务端 `services/cors-probe.ts` 已有探测，确保 `direct/hls/dash` 都写入 `cors` 字段
   （HLS/DASH 现在只用响应头推断，建议改为统一 `probeCors`）。
2. **HLS/DASH 接入回退**：与 `DirectPlayer` 对齐——遇到不支持/网络类错误且

## C-2 弱网/慢设备周期性硬跳（代码分析；工作区已部分改进）

**现象**：设备持续落后于房间时间时，会出现周期性「卡一下」（暂停 + 寻址 + 恢复），
观感比缓慢落后更糟。

**根因（线上版本 `main`）**：`client/src/util/playback-sync.ts`

- 硬跳阈值：`magnitude > 1`（`:222`）即 `await seek(...)`，`seek()` 内部
  `media.pause()` → 设置 `currentTime` → 等待恢复（`util/media-seek.ts`）。
- 冷却：`Date.now() - lastSeekAt >= (buffering || bufferedSinceLastSeek ? 8000 : 2000)`（`:135`），
  即最密每 2 秒一次；速率微调上限只有 8%（`MAX_BEND`，`:37`），
  8 秒追赶截止（`BEND_DEADLINE_MS`）后也会回退成一次 seek。

**现状**：工作区分支已经改了策略——硬跳阈值提到 3 秒（`HARD_SEEK_DRIFT`），
1–3 秒区间用最高 15% 的「追赶」（`CATCHUP_MAX_BEND`），截止时间放宽到 8–30 秒
（`playback-sync.ts:35-53, 269-272`）。也就是说**慢设备的常见场景已经缓解**。

**修复方案**：

1. 把工作区的策略合并上线后，用真实设备（弱网 + 低端机）实测「持续落后」场景，
   记录硬跳次数与感知（建议在 `docs/playback-sync.zh-CN.md` 补一节实测数据）。
2. 增加「落后归因」：当短时间内连续两次硬跳且每次都在缓冲，则临时放宽阈值
   （例如 3s → 6s）并优先提示网络问题，而不是继续抖动。
3. 可选：对「本机解码能力不足」的情况（`droppedVideoFrames` 快速增长、CPU 时间占比高）
   给出低码率建议或自动降档，而不是靠 seek 追。

**验证**：Chrome DevTools 限速到 1.5 Mbps 播 1080p，10 分钟内硬跳次数 ≤ 2 且每次
暂停 < 300ms；恢复网络后 10 秒内回到同步且不再硬跳。

## C-7 缓存 TTL 判定方向写反（代码分析）

**现象**：可缓存服务（YouTube/Vimeo 等）的标题、描述、封面、时长一旦入库就不再刷新；
如果视频时长后来变化，房间时钟与「自动下一集」判断会跟着错。

**根因**：`server/storage/cachedvideo.ts:84-85`

```ts
const isCachedInfoValid =
    lastUpdatedAt.diff(today, "days") <= (origCreatedAt.diff(today, "days") <= 7 ? 7 : 30);
```

`dayjs().diff(today, ...)` 得到的是「过去 − 现在」的**负数**，`负数 <= 7` 恒为真，
于是 `isCachedInfoValid` 永远为 `true`；后半段 `origCreatedAt` 的比较同样恒真。

**修复方案**：

1. 改为「经过的天数」比较：

```ts
const ageDays = today.diff(lastUpdatedAt, "days");
const intervalDays = today.diff(origCreatedAt, "days") <= 7 ? 7 : 30;
const isCachedInfoValid = ageDays <= intervalDays;
```

2. 顺手补一条单元测试：构造 `updatedAt = 现在 - 40 天`、`createdAt = 现在 - 100 天`
   的缓存记录，断言 `isCachedInfoValid === false`；再构造 1 天前的记录断言为 `true`。
3. 与 P1-2 的「失败短缓存」区分开：这条只影响可缓存服务的刷新，不影响直链探测缓存。

**验证**：单测通过；线上把某条 YouTube 记录的 `updatedAt` 手工改旧，重新解析时应触发刷新。

## C-8 探测无字节预算/并发闸、清单拉取无超时、错误码固定（代码分析）

**现象**：慢源或不透明（不支持 Range）的源会长时间占用探测进程；上游清单卡住时服务端
一直挂着；不同性质的错误在客户端看起来完全一样。

**根因**：

- `server/ffprobe.ts:270-292`（`RunFfprobe`）只设了 `-rw_timeout 12s` 与 35 秒硬超时，
  **没有** `disk` 策略里的 `preview_max_bytes`（`:371`），也没有并发闸；
  生产容器只有 `1 CPU / 512 MiB`（`deploy/next-compose.yml:62-67`）。
- `server/services/hls.ts:53,99` 与 `server/services/dash.ts:56` 的 `axios.get` **未设置 timeout**。
- `server/api/data.ts:69` 对所有命名错误硬编码 400，忽略了
  `server/exceptions.ts` 里 `FfprobeTimeoutError.status = 408`、`FfprobeError.status = 502`
  等定义；SSRF 防护抛出的普通 `Error`（`server/ffprobe.ts:62-80`）则落到 500/`Unknown`。

**修复方案**：

1. 给 `RunFfprobe` 增加「按主机/全局并发闸」（简单实现：`p-limit` 或自建计数信号量）
   与「已读字节上限」（可复用 `counterBytesDownloaded` 指标，超限主动 kill 并返回超时文案）。
2. 给 HLS/DASH 的清单请求加 `timeout: 8000`，并把失败包装为 `M3u8ParseError` 一类的命名错误。
3. `api/data.ts` 改为读取异常自带 `status`；把 `assertPublicMediaUrl` 的拒绝包装成具名
   `OttException`（含中文 `userMessage`），前端按 `name` 映射文案（沿用现有
   `client/src/util/server-error.ts` 的机制）。

**验证**：用一个故意不响应字节的地址连续探测，容器 CPU < 50%、p99 响应 < 40 秒；
HLS 清单挂起时 8 秒内返回中文错误；SSRF 拒绝返回可读文案而不是「未知错误」。

## C-9 无国内站点适配器、不中转媒体、首页示例为海外源（代码分析，产品级）

**现象**：粘贴 B 站/优酷/爱奇艺链接得到「暂不支持此链接」；无 CORS 或防盗链的片源只能
靠客户端自救；首页「我可以添加什么？」给的例子是 YouTube/Vimeo/海外 CDN。

**根因**：

- 支持列表只有海外服务：`common/constants.ts:12-25` 的 `ALL_VIDEO_SERVICES`
  （youtube/vimeo/googledrive/reddit/tubi/peertube/pluto/invidious/odysee/direct/hls/dash）；
  `server/infoextractor.ts:182-188` 找不到适配器即抛 `UnsupportedServiceException`。
- 服务端不中转媒体：全仓没有媒体流式端点，`OmniPlayer.vue:95/111/132` 直接用
  `source.id`/`hls_url`/`dash_url` 取流；`cors_proxy` 配置只被 Pluto 使用
  （`server/services/pluto.ts:219-230`）。
- 与服务器上独立运行的 `ott-resolver.service`（getlink.py）之间**没有任何调用关系**，
  应用既不会调用它，也没有降级路径。
- 首页示例来自 i18n（`client/src/locales/zh-CN.ts` 的 add-preview 文案），是上游默认值。

**修复方案（分档，先做 1 与 2）**：

1. **示例与文案本地化（小时级）**：把「我可以添加什么？」的示例换成国内可达的直链/HLS
   样例（自建静态文件或公开 CDN），并补一行「也支持带签名的直链，需源站允许跨域」。
2. **外部解析器兜底（天级）**：新增 `cn-resolver` 适配器，把「未识别 URL」交给
   本机的 `ott-resolver`（HTTP 接口，带 3–5 秒超时与一次重试），返回 `{title, url, mime}`
   并注册为 direct/HLS 项。安全上限制：只允许解析出 http/https 公共地址，
   结果走 `assertPublicMediaUrl`；失败时明确回落到「暂不支持」文案并给出原因。
3. **受限中转（按需，成本敏感）**：为无 CORS/防盗链源提供 Range 中转端点
   （仅限 direct 与 HLS 分片，限制并发与总带宽、白名单协议、禁止大文件整段缓存），
   作为「本机直连失败」后的显式回退，并在 UI 上标注「经由服务器中转」。
   这条要单独评估带宽成本与滥用风险（见 `docs/deployment-options.zh-CN.md` 的资源口径）。
4. **文档**：在 `docs/media-parsing.zh-CN.md` 写清「哪些链接能加、失败时的判定顺序」。

**验证**：示例链接可直接播放；粘贴 B 站链接时若 `ott-resolver` 可用则解析成功，
不可用时给出「暂不支持 + 原因」而不是笼统报错。

## C-12 同步锚点少算一次单向网络延迟（仅线上版本；工作区已修）

**现象**：线上版本里所有客户端的房间位置系统性偏晚约 RTT/2；本机自测无感，跨地域用户会
表现为「总是差一点点，然后被微调」。

**根因（线上版本 `main`）**：服务端在**发送**同步消息时锚定 `playbackPosition`，客户端在
**收到**时直接 `playbackStartTime = dayjs()`（`main:client/src/stores/room.ts:92,99`），
`computeCurrentPosition` 从接收时刻起算，缺一段网络传输时间。

**现状（工作区已实现补偿）**：`client/src/util/connection-latency.ts:29-34` 用最小 RTT
样本的一半作为单向延迟估计，`client/src/stores/room.ts:51-53` 的
`syncAnchorNow()` 在锚定时减去它，同步动作统一改用该函数。也就是说这条**在本地分支已修**，
上线后只需验证延迟估计在弱网下不引入过冲。

**修复方案**：

1. 直接采用工作区实现上线，并确认采样重置时机：`resetLatencySamples()`
   应在重连/换房间时调用，避免旧样本污染新连接。
2. 采样来源建议保留多条（WebSocket ping 或应用层往返），取最小值以减少抖动；
   在播放详情面板里显示「估算单向延迟」，便于用户与维护者核对（可选）。
3. 若个别环境 RTT 波动极大（移动网络），给补偿设上限（例如 ≤150ms），
   避免过补导致「反向落后」。

**验证**：跨地域或人为加 200ms 延迟，双端实测「与房间偏差」中位数从 +100ms 降到 ±30ms；
漂移微调频率下降；重连后第一帧不出现明显跳跃。
