# 缓冲时一起暂停

房间只有一名观众时**始终生效、不看开关**：唯一观众（需具备播放 / 暂停权限）自己的缓冲就暂停房间
时钟，位置不会在缓冲期间继续向前跑，恢复后也不会因为时钟跑远而把卡住的一段直接跳过。多人房间由
房间设置中的“缓冲时一起暂停”控制（默认关闭，具有“其他房间设置”权限的人可以开启）：开启后，只要
拥有播放 / 暂停权限的观众中有人明确上报正在缓冲，房间就一起暂停，缓冲解除或等待方离开后恢复。
提示列出正在缓冲的观众；手动暂停时也可能显示缓冲提示，它只说明观众状态，不代表系统自动暂停了房间。

每次开始或恢复播放有 2 秒宽限。一次等待到 15 秒时强制继续，之后 30 秒内不再因缓冲
自动暂停；超时通过现有 1 秒房间更新周期检查。手动播放会释放等待并进入冷却，手动暂停
则撤销自动恢复意图。临时 2×、播放准备握手、换源和房间清空都有单独的释放逻辑。
门的建立 / 释放 / 超时在服务端日志各写一行 info（等待者与原因），便于线上复核。

“换源”本身也是一道闸门：出队下一集、跳过或「立即播放」把新片源交给房间时，时钟先停在
片头（`holdPlaybackForPreparation`），由准备握手在首位观众出帧后启动；准备不了的服务
（外嵌播放器、直播）仍立即开始。这道闸门不产生暂停意图之外的状态，手动播放同样可以越过；
它与本页的缓冲等待互斥——有待确认的准备时缓冲等待不会接管。

后台标签页的缓冲主动报告为就绪，避免旧的缓冲状态留在服务端；切回前台立即报告真实状态。
自动播放受阻、播放错误和还没上报状态的观众不作为等待方。不具备播放 / 暂停权限的观众
也不能冻结房间。浏览器可能限制后台下载，这是排除后台等待的明确取舍。

## 诊断遥测（v1.4.18）

服务端原来只知道“某观众在缓冲”，不知道原因。现在客户端每 5 秒、以及刚进入缓冲的瞬间，通过独立的
`diagnostics` WebSocket 动作上报一份快照；服务端在 `buffer gate engaged` 日志行追加
`diagnostics=[{...}]`，每个等待观众一条。

快照包含：缓冲前瞻与 `bufferGrowth`（每秒墙钟实际缓冲的媒体秒数，判断真实吞吐）、`readyState` /
`networkState`、隐藏标签页 / 暂停 / 自动播放受阻、起播与重缓冲计数、房间 WebSocket RTT、
`navigator.connection` 的类型/下行/RTT（仅 Chromium）、HLS 带宽估计与当前档位、总帧/丢帧、错误码。
来源只记录 host，不记录完整 URL、签名或查询串；快照只存在房间内存，不进 Redis、数据库或同步载荷，
并且作为独立动作发送，**不会改写 `playerStatus`**，因此不会提前释放或抖动缓冲门。

这组字段能区分：下行不足（`bufferGrowth` 远小于 1）、RTT 高（`wsRttMs` / `connectionRttMs`）、后台
标签页（`hidden`）、自动播放受阻（`autoplayBlocked`）、解码吃力（`droppedFrames`）以及 HLS 选档偏低。

## 保存与部署

`bufferGateMode` 使用 `off` / `pause` 两个值，贯穿设置 API、房间同步、Redis 和持久房间。
数据库迁移 `20260912090000-add-buffer-gate-mode.js` 给实际表 `Rooms` 新增默认 `off` 的列，
已有房间保持关闭。部署 compose 会先运行迁移；迁移失败时不启动新应用。回滚应用可以保留
这列，必须降库时才在备份后执行迁移回退。

等待名单、开始时间和冷却时间只在内存中。保存 Redis 快照时保留“下次加入继续播放”的意图，
避免自动暂停后重启或空房间造成永久停播。Cloudflare 预览后端暂不实现此功能，其设置入口
隐藏，旧服务端缺少字段时客户端按关闭处理。

## 验证范围

自动化覆盖状态机、单人免开关与多人开关语义、权限、手动操作、15 秒超时 / 30 秒冷却、临时倍速、
握手、空房间恢复、API 校验、数据库及 Redis 往返，以及前端遥测和设置提交。网络故障模拟与实际浏览器结果
见发布验证记录。低端安卓的出帧、音频连续性和蓝牙输出延迟仍需要真实设备测量。
