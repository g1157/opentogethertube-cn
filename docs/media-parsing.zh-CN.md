# MP4 直链解析、等待与排查

“浏览器能播放”与“添加面板能取得媒体信息”是两个步骤。添加视频时，后端先读取时长、媒体类型等信息，
用于队列、跳转和全房间时钟；进入播放器后，各观众的浏览器再直接读取并解码片源。
前一步失败或超时，不等于文件无法播放，也不应直接要求用户重新转码。

## 文件尾部索引为什么会导致长时间转圈

MP4 的 `moov` 保存时长、轨道和采样索引，`mdat` 保存音视频数据。有效 MP4 可以将 `moov` 放在文件头部，
也可以放在 `mdat` 后面。浏览器通常能通过 HTTP Range 跳到尾部取得索引。

旧 Node.js 默认 `FFPROBE_STRATEGY=stream`：Axios 从头顺序读取文件，将字节喂给 ffprobe 的标准输入。
标准输入不能随机跳转；遇到尾部索引，可能要先读完整段媒体才能得到信息，最后触发 35 秒超时，
或在探测进程没有返回有效轨道时被报告为缺少媒体信息。索引在前的小 MP4 可能一直正常，因而容易误判为链接失效。

本次报告的文件是 251,800,351 字节（约 240.1 MiB），尾部 `moov` 从字节 250,928,242 开始，大小为
872,109 字节；时长 1,421.09 秒，包含 H.264 1080p 视频和 AAC 音频。2026-09-11 的调查中，旧原站
接口发生约 36 秒的探测超时，而容器中的 ffprobe 直接读取 URL 能成功返回元数据，正常退出。
这项对比说明失败发生在探测路径，不能据此认定媒体损坏。

## 两版的处理方式

| 部署方式 | 当前实现 | 资源与等待边界 |
| --- | --- | --- |
| Docker / Node.js | 默认 `run`，ffprobe 直接读取 HTTP(S) URL，允许 Range 跳到尾部索引 | 单次网络 I/O 最多等待约 12 秒；探测进程总上限 35 秒；没有固定的下载字节预算 |
| Cloudflare | 不运行 ffprobe；以最多 4 KiB 的块读取必要的 MP4 结构、时长和轨道，跳过音视频数据及大的采样表 | 每操作/批次总预算 2 MiB、16 次实际 fetch（含重定向）、20 秒；每次读取最多约 12 秒 |
| 共用添加面板 | 展示读取信息和慢响应提示；超时后提供重试 | 请求开始后最多等待 45 秒；输入变化、清空或组件卸载会取消旧请求，旧结果不能覆盖新链接 |

Cloudflare 曾对本案例返回片源读取超时；单独诊断时同一源的 Range 请求也能很快返回缓存结果。
源站缓存、出口位置和网络状态会改变耗时，不能把一次成功当作永久可达保证。新的解析器减少了等待的工作量：
无需为了两个字段下载整个 0.83 MiB 的 `moov`，也不再仅因无关采样表使索引超过 2 MiB 就拒绝文件。
它仍保留请求、字节、期限和结构复杂度限制，无法替代通用媒体解码器。

两版都不会通过应用持续中转完整视频，也没有视频转码功能。Node.js 的 `run` 依赖片源支持合理的 HTTP
读取和跳转；对不支持 Range、持续慢响应或特殊容器的源，仍可能读取较多字节或超时。不能将其描述为
“所有 MP4 恒定只读头部”或承诺每条链接一秒完成。

## Docker 配置及已有实例升级

代码默认值、`deploy/base.toml`、`deploy/next.Dockerfile` 和 `deploy/next-compose.yml` 均使用 `run`。
新实例的 `.env` 示例包含：

```dotenv
FFPROBE_STRATEGY=run
```

已有实例应检查实际 Compose 配置和容器环境，显式设置的 `FFPROBE_STRATEGY=stream` 会覆盖新默认值。
更新镜像及配置后需要重建应用容器，单纯重启旧容器不会改变其环境变量。按
[部署与回退文档](../DEPLOYMENT.md) 先在独立端口验收，然后推广同一镜像；不需要为本修复迁移数据库。

可只读取这一项配置，避免输出完整环境中的数据库密码和 API 密钥：

```sh
sudo docker exec YOUR_APP_CONTAINER printenv FFPROBE_STRATEGY
```

`stream`、`disk` 仍保留给已有部署的兼容用途。显式继续使用它们时，需要承担各自的顺序读取或临时磁盘限制，
不要再依赖未设置环境变量来选中旧默认值。Cloudflare 版没有这个配置，也不需要安装 ffprobe。

## 如何区分故障阶段

| 现象 | 检查内容 |
| --- | --- |
| 添加后转圈，没有预览条目 | 浏览器中 `/api/data/previewAdd` 的状态、错误信息和耗时；Node 的探测策略及源站可达性 |
| 有预览条目，但播放器无法加载 | 浏览器的视频请求、CORS、HTTPS 混合内容、Cookie/防盗链、解码支持和真实媒体错误 |
| 已有画面且能播放，仍显示等待 | [播放器就绪判定](player-interactions.zh-CN.md)；不属于添加阶段，也不是要求缓冲到某个百分比 |
| 只有 Cloudflare 版失败 | 同时检查 Worker 出口能否访问片源、Range 响应、探测预算及账户额度；本机可达不代表 Worker 可达 |
| 出现 429 或大量 API 同时失败 | 区分应用限流和 Cloudflare 账户额度，参照 [用量文档](cloudflare-quotas.zh-CN.md) |

源站应返回正确的 `Content-Type`，支持需要的 Range，分段响应的 `Content-Range` 必须与请求一致。
HTTPS 页面应使用可访问的 HTTPS 媒体地址。播放器使用 `crossorigin="anonymous"`，因此原生 MP4 同样需要
片源允许跨域；直接打开链接能播放，不证明嵌入其他站点时的跨域访问也被允许。

诊断下载应优先使用 HEAD 和受限 Range，避免为了查看响应头先下载整个文件。测试 ffprobe 时，保留完整
JSON 和真实退出码；将输出接到 `head` 可能引发 SIGPIPE，不能仅凭被截断的输出判断整个探测过程成功。
不要在公共日志中放入私有片源的签名参数、Cookie 或完整认证请求头。

## 回归验证

- Node.js 用真实 ffprobe 和本地 HTTP Range 服务测试一个尾部索引在 32 MiB 之后的虚拟 MP4；
  限制实际传输量小于 2 MiB，验证可以取得时长，防止退回顺序下载。
- Cloudflare 在真实 workerd 环境中验证大索引、64 位时长、纯音频和先音频后视频的轨道顺序，
  并保留错误分段、无 Range、无效结构、批次预算和重定向边界测试。
- 添加面板模拟永远不返回的请求，验证超时、重试、输入取消以及旧响应不能覆盖新结果。

上述自动化验证不依赖报告片源持续在线；上线验收另外检查真实远程链接及浏览器解码。
