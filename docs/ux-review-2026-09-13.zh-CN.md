## P0-1 添加视频探测失败会把观众踢出房间（实测确认）

**现象**：在房间内添加一个服务端 `ffprobe` 探测失败的视频源时，发起者的 WebSocket 被
服务端以关闭码 `4000` 断开；页面显示"已断开连接 —— 发生了一些事情，但我们不知道是什么。
请将此报告为 Bug。"，并且不会自动重连，只能手动重新进入房间。房间里其他成员不受影响。

**复现（2026-09-13 实测）**：

1. 进房后打开"添加"页，填入一个服务端会探测超时的 URL（本次为
   `https://vjs.zencdn.net/v/oceans.mp4`，跨境网络抖动时超时；该源在预览阶段成功、
   添加阶段超时）。
2. 点击预览卡上的"立即播放"。
3. 客户端被踢：浏览器 console `dispatching event {kind: "kicked", reason: 4000}`，
   页面出现"已断开连接"覆盖层。

**证据（服务端日志）**：

```text
Failed to get video info for direct:https://vjs.zencdn.net/v/oceans.mp4:
  ffprobe exit code 1 signal none stderr=[tcp @ ...] Connection to
  tcp://vjs.zencdn.net:443 failed: Operation timed out
Failed to process client (id=..., room=...) message (action=req):
  Error: ffprobe exit code 1 ...
Unknown error type, kicking client
```

**根因**：`server/clientmanager.ts:266-279`（`onClientMessage` 的 catch）。凡是不属于
`OttException`（且不是 `MissingToken`）的错误一律 `client.kick(OttWebsocketError.UNKNOWN)`。
`ffprobe` 子进程失败/网络错误是普通 `Error`，于是"元数据探测失败"被当成"连接级异常"处理。
同类路径上任何未预料到的错误都会以同样方式踢人。HTTP 预览路径（`/api/data/previewAdd`）
对同种失败有优雅处理，两条通道行为不一致。

**修复方案**：

1. 服务端：请求处理错误不再默认踢人。把 `onClientMessage` catch 的默认分支改为
   "记录日志 + 通知发起者"，仅在明确的连接级错误（缺 token、鉴权失败）时 kick。显式
   踢人已经有独立通道（`handleCommand`，`server/clientmanager.ts:588-593`）。
2. 让元数据失败成为可预期错误：`server/ffprobe.ts` 在 exit code ≠ 0 时抛
   `FfprobeError extends OttException`（新增；超时继续用已有的 `FfprobeTimeoutError`，
   `server/exceptions.ts:108`）。`services/*.ts` 的 `fetchVideoInfo` 失败路径同样包装，
   保证上层能按类型分流而不是落入"未知错误"。
3. 给用户可见反馈：本仓库 `common/models/messages.ts` 的 `ServerMessage` 联合中
   没有 error 消息类型，客户端 `client/src/store.ts:94-101` 的 `error` action 目前
   没有生产者。建议补一条 `ServerMessageError { action: "error"; name: string; message?: string }`，
   由 clientmanager 在请求失败时发给发起者；客户端按 `name` 映射 zh-CN/en 文案，
   未知 name 显示通用文案。快速缓解可先复用已有的 `eventcustom` 通道发一条提示，
   等带类型的错误消息落地后替换。
4. 与 P1-7 配合：被踢覆盖层不再显示"请将此报告为 Bug"。

**验证**：用一个必然不可达的地址（例如防火墙上 REJECT 的自建端口）在房间内执行添加，
期望收到"无法读取视频信息"一类的错误提示、连接保持、其他观众不受影响；随后用正常源
添加成功。再故意触发一次其它未预期错误，确认不会被踢出。

## P0-2 无 CORS 头的片源无法播放，且错误提示误导（实测确认）

**现象**：某些直链 MP4 在 OTT 里显示"不支持的视频或来源 / 视频格式可能不受支持，或
视频链接已失效"，但同一个链接在浏览器地址栏直接打开可以正常播放。用户会误以为是自己
的片源坏了。

**控制变量实验**：在同一页面、同一浏览器、同一个 URL
（`https://media.w3.org/2010/05/sintel/trailer.mp4`）下创建两个 video 元素：

| 元素 | 结果 |
| --- | --- |
| `<video crossorigin="anonymous">` | 立即 `error code 4 (MEDIA_ELEMENT_ERROR: Format error)`，readyState 0 |
| `<video>`（无该属性） | `loadedmetadata` → `canplay`，readyState 4，正常就绪 |

对照源（响应带 `access-control-allow-origin: *`）：
`cdn.jsdelivr.net/gh/mediaelement/mediaelement-files@master/big_buck_bunny.mp4` 在房间内
添加并播放正常（实测），`vjs.zencdn.net/v/oceans.mp4` 也带 `ACAO: *`。
`media.w3.org` 的响应没有任何 `Access-Control-Allow-*` 头。

**根因**：`client/src/components/players/DirectPlayer.vue:8` 硬编码
`crossorigin="anonymous"`（服务于字幕 track 与画质增强的 WebGL 贴图）。跨域模式下，
源站未返回 CORS 头时，浏览器直接判定资源不可用（Chrome 表现为 MEDIA_ERR_SRC_NOT_SUPPORTED
/code 4）。播放器没有降级路径，`OmniPlayer.vue` 的错误文案把原因说成片源格式问题。

**修复方案**（建议组合）：

1. 探测降级：模板改为动态绑定 `:crossorigin="corsEnabled ? 'anonymous' : undefined"`。
   首次在 `direct`/`hls`/`dash` 源上遇到 metadata 阶段失败（`MEDIA_ERR_SRC_NOT_SUPPORTED`）
   时，移除 crossorigin 重试一次。降级后自动关闭画质增强并在提示中说明原因（无 crossorigin
   时 canvas/WebGL 会因贴图污染不可用，跨域字幕 track 也可能加载失败）。
   实现位置：`DirectPlayer.vue` 与 `client/src/util/media-recovery.ts` 的恢复流程。
2. 修正错误文案：`player.playback-error-title.unsupported` 与对应说明不再断定"格式不支持"，
   改为列出真实可能（源站未允许跨域 / 格式确实不支持），并引导用户用"仅重载我的视频"
   重试、或关闭增强后重新添加。
3. 长期可选：添加时由服务端探测源站 CORS 头（小范围 GET），把 `cors: boolean` 写进
   视频元数据；客户端据此决定增强/字幕能力与提示文案，避免先失败后重试。

**验证**：用无 ACAO 的 MP4（如上面的 w3.org 样例）添加并播放，期望可直接播放、增强自动
关闭、console 无 code 4；用带 ACAO 的源（jsdelivr 样例）确认增强仍可用。两组都要求
错误提示与实际原因一致。

## P0-3 新观众进入正在播放的房间时没有引导，点击控制栏会暂停全房间（实测确认）

**现象**：新会话直接打开一个正在播放的房间链接（无任何点击），本机视频不动，但界面显示
"正在播放 big_buck_bunny"、时间轴在走、控制栏按钮呈暂停态；界面上没有任何"点击播放加入"
的提示。此时点击控制栏的播放/暂停按钮，实测**把整个房间暂停了**（见实验记录），而不是让
本机开始播放。

**实验记录**：

- 会话 A：添加并播放 `big_buck_bunny`（`t≈2.6s`，播放中）。
- 会话 B（全新会话、无用户手势）：打开同一房间 URL。检查 video 元素：
  `paused: true, t≈21.2s`（停在房间位置），界面显示"正在播放"、按钮为暂停态。
- 在 B 点击播放/暂停按钮后：A、B 两个会话的 video 元素同时停在同一位置（`t=1.59`）。
- 之后在 A 点击播放：A、B 恢复播放且时间差仅 `0.01s`（5.24 vs 5.25），说明同步本身正常。

**根因（代码分析）**：`Room.vue` 已有 `mediaPlaybackBlocked` 与 `onClickUnblockPlayback`
（`client/src/views/Room.vue:856-923`），`togglePlayback` 也有"blocked 时本机解锁而不是
发暂停请求"的分支（:1031-1032）；`OmniPlayer` 收到的 `playbackBlocked` 仅用于隐藏加载
提示（`client/src/components/players/OmniPlayer.vue:288`），没有独立的解锁 UI。
但实测中该路径没有覆盖"加入正在播放的房间"这一场景：要么 blocked 未及时置位，要么
播放准备流程在等待用户手势而界面没有表达。具体时序需要按下面的复现步骤进一步定位。

**修复方案**：

1. 新增明确的"点击加入播放"遮罩：当"房间在播 + 本机未播 + 非用户手动暂停"时，
   在播放器上显示大播放按钮与文案（示例："房间正在播放，点击加入"）。点击调用
   `onClickUnblockPlayback()` 的现有逻辑（需从 OmniPlayer 上抛事件到 Room）。
2. 状态判定改为组合条件而非单一标志：做一个 computed（如 `shouldJoinPlayback`），
   同时覆盖入房恢复、seek 中断、标签页切回、切换片源等场景，并与缓冲联动
   （`BufferGateNotice`）和播放准备流程的优先级定义清楚。
3. 核对 blocked 置位时机：入房首播被浏览器拒绝（NotAllowedError）时必须置位；
   若准备流程刻意等待用户手势，也要进入同一 UI 状态，不能静默。
4. 控制栏按钮语义复核：在"本机未播但房间在播"时，点击应执行本机解锁（现有 :1031
   分支的意图），确保该分支真的命中；全房间暂停仍应通过明确的暂停按钮触发。
5. 文案：zh-CN / en 增加对应 key。

**验证**：双会话测试——A 播放大视频；B 用全新会话打开房间链接，期望出现"点击加入播放"
遮罩；点击后 B 开始播放、A 的播放状态不被打断；在 A 暂停后 B 的遮罩与状态正确变化。

## P0-4 有人加入房间时，全房间被强制对齐位置而短暂卡顿（实测+代码确认）

**现象**：房间里有人加入时，正在观看的所有人会感到画面极短一卡（约 0.2–0.3 秒的冻结），
随后可能有一小段速度略快（±8% 速率上限）的追赶。用户描述为"用户进来会极短卡顿一下"。

**复现（2026-09-13 实测）**：

1. 会话 A 播放视频，安装媒体事件插桩（video 的 pause/seeking/seeked/playing/ratechange）。
2. 会话 B（独立浏览器）打开房间链接加入。
3. A 的元素在加入窗口出现 `pause → seeking → seeked → playing` 序列，从暂停到恢复约
   280ms；随后 `ratechange` 到 1.08（+8% 上限）保持十余秒用于追赶。
4. 对照：B 自己的播放器在加入时从 0 跳到房间位置（新观众必须的对齐，属预期行为）。
   B 离开房间时，A 未出现任何媒体事件。

**根因（代码确认）**：

- 服务端：`server/room.ts:1676-1677`（`joinRoom`）在每次有人加入时，向**整个房间**广播
  一条带播放位置的同步：

  ```ts
  // HACK: force the client to receive the correct playback position
  await this.publish({ action: "sync", playbackPosition: this.realPlaybackPosition });
  ```

  注释说明本意是让"加入者"拿到正确位置，但 `publish` 面向全房间。

- 客户端：`client/src/views/Room.vue:723-727` 对任何携带 `playbackPosition` 的同步都会
  请求重新对齐：

  ```ts
  if (msg.playbackPosition !== undefined || "currentSource" in msg) {
      if (!playbackPreparationState.value.active) {
          void playbackSync.requestSeek();
      }
      ...
  ```

- `client/src/util/playback-sync.ts:228-233` 的 `requestSeek()` 设置 `pendingSeek`，
  在 `tick()` 中走 `if (pendingSeek) { await seek(state); return; }`（:158-161）。
  这条路径**绕过了漂移纠正的阈值与冷却**（正常漂移超过 1 秒才硬寻址，0.15–0.3 秒用速率微调）。

- `client/src/util/media-seek.ts:5-22` 的 `seek()` 只要 `|currentTime - 目标| > 0.05` 秒
  就执行 `media.pause()` → `media.currentTime = position`，即一次真实寻址：
  先暂停、再设位置、等数据恢复。这就是可感知卡顿的来源。

**为什么是"有时候"**：`media-seek` 有 50ms 容差。偏差在 50ms 以内时什么都不会发生；
而服务端位置与客户端本地的差值天然包含网络传输时延与解码延迟，常见在 100–300ms，
因此多数加入会触发寻址。网络越快、客户端越"准"的时候才不卡。

**离开方向**：代码层面没有对应机制——离开只广播 user 更新
（`server/clientmanager.ts:418-424`），客户端对 users 变化没有任何播放副作用
（`UserList.vue` 仅清理菜单状态，`Room.vue` 的播放相关 watcher 不含 users）。
实测在离开瞬间也没有媒体事件。若用户确实感知到"出去也卡"，应优先排查下面的
漂移纠正寻址，而不是离开路径本身。

**附带观察（需后续确认）**：稳定播放过程中也记录到无成员进出的 `pause → seek → play`
事件（约 0.2–0.3 秒），与漂移纠正的兜底寻址一致（`playback-sync.ts:186-208`：
`|drift| > 1s` 直接 seek；速率微调达到 8 秒截止后也回退为 seek）。本次测试场景中曾多次
重复添加同一视频，可能人为制造了位置重置（房间位置归零而本地继续播放），因此这些事件
的具体触发原因留给后续带"寻址原因日志"的验证，不作为结论。

**修复方案**：

1. 服务端（推荐，低风险）：`joinRoom` 的这条"强制同步"只发给加入者本人。它的目的
   （新客户端拿到正确位置）只需要单播；其余成员的位置没有变化，不应被打断。实现上可在
   `clientmanager` 处理 JoinRequest 成功后向该 `client.send({ action: "sync", playbackPosition: room.realPlaybackPosition })`，
   或让 Room 提供面向单客户端的同步通道。
2. 客户端（防御性）：为"同步触发的重新对齐"增加合理门槛——偏差小于约 0.3 秒时交给既有
   速率微调（`BEND_START`），只有更大偏差才执行硬寻址，并保留冷却。这样即使服务端仍广播，
   小偏差也不再造成冻结。
3. 可观测性：在 `seek()` 调用点记录原因（join-sync / drift / 用户操作 / 解锁），下次复现
   时可直接确认来源；`media-seek.ts` 的 50ms 容差建议提为常量并配注释。
4. 与 P0-3 一并验证：加入者自身的首次对齐（从 0 跳到房间位置）是必要的，修复不应影响
   新观众拿到正确进度。

**验证**：

- 双会话：A 播放（插桩监听 pause/seeking/seeked/playing），B 加入 → A 在加入窗口不应出现
  `pause/seeking`（允许 `ratechange` 微调）；B 的进度仍正确。
- B 离开 → A 无任何媒体事件。

## P1-7 被踢提示不可读且不重连（实测确认）

**现象**：被踢后覆盖层显示"已断开连接 —— 发生了一些事情，但我们不知道是什么。请将此
报告为 Bug。"，没有原因、没有重试按钮；`connection.ts` 对 `code >= 4000` 直接终止且
不再重连。

**根因**：关闭码 `4000 = UNKNOWN`（`common/models/types.ts`）没有对应的用户文案
（`connect-overlay.dc-reasons.*` 未覆盖）；客户端 `client/src/plugins/connection.ts:205-220`
把任何 `>= 4000` 的关闭都视为终止。而 P0-1 让服务端大量使用 `4000`。

**修复方案**：

1. 服务端：按 P0-1 不再用 `UNKNOWN` 踢人；真的需要断开时使用语义明确的码
   （`ROOM_NOT_FOUND` / `ROOM_UNLOADED` / `KICKED` 等已有值）。
2. 客户端文案：为可能出现的每个码补 zh-CN 文案；未映射的码显示"连接被中断"+可读建议，
   不出现"报告 Bug"字样（或仅在真正未知码时保留，但配合可重试）。
3. 重试入口：`RoomDisconnected.vue` 增加"重新连接"按钮。对 `UNKNOWN` 类可做有限次
   自动重连（如 1–2 次退避），失败后再显示覆盖层；`KICKED`、`ROOM_NOT_FOUND` 保持
   不重连但给出准确原因。

**验证**：分别用"管理踢人"（4005）、"房间不存在"（4002）、人为构造的 4000 场景检查
覆盖层文案与重连行为。
