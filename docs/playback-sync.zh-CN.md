## 换片就绪与兜底（Playback Start v2）

换片、自动下一集、跳过和“立即播放”不再指定单个 preparer，而是创建一个准备轮次：

- 回合开始时快照所有有播放权限的观众（`eligible`）；回合开始后加入的人不阻塞本轮。
- 每个 eligible 客户端在**首帧已经渲染且缓冲前瞻达到跑道**后上报 ready：
  - 直链 MP4：3 秒；
  - HLS / DASH：6 秒；
  - 浏览器不暴露 `buffered` 时按未知处理，不拿 0 秒阻塞房间。
- 客户端握手分三段（`playback-preparation.ts`）：
  1. **对齐与首帧**：定位到本轮位置并播放，直到目标位置确实出帧。“反复错过位置”的失败判定
     （两次重定位）只在这一段有效。
  2. **跑道**：跑道从**目标位置**量（`currentTime + bufferAhead − 目标`），不随播放头移动。
     跑道不够时先暂停等待（阶段 `buffering`），画面停在首帧；暂停 2 秒内跑道增长不足 0.25 秒
     （部分移动浏览器暂停时不缓冲）则本轮改为播放着等。跑道慢不会让客户端判失败，是否继续
     等由服务端的 8 秒 / 20 秒期限决定。
  3. **停靠**：跑道够了之后暂停并精确回到本轮位置（阶段 `parking`），seek 完成且重新出帧后才
     回执，回执里带的是元素实际停靠的位置（服务端仍据此校验，房间一律从本轮位置起播）。
     停靠只 seek 一次，落点在 0.25 秒内即接受。
- 准备期间本机音量乘 0（`preparationFactor`，与语音压低的 `duckFactor` 同一机制），房间真正
  开始播放、本轮取消或离开房间时恢复；不使用 `muted`，避免无手势取消静音被自动播放策略暂停。
  iOS 上 `volume` 只读，这条不生效。
- 全体 ready：多人房间在 `startAt = now + 1s` 定时开始，单观众立即开始。服务端把房间时钟锚在 `startAt`；已回执且时钟偏移已知的客户端在这一刻本地起播（见“房间时钟的锚定”），其余客户端在收到 `isPlaying` 时起播。内部使用相对定时器，回调带一个“已到期”标记，系统时钟回拨不会让房间卡住；
- 8 秒内未全体 ready：带已经 ready 的人开始（partial）；
- 8 秒内无人 ready：保留准备轮次，全房显示“开始播放”按钮；
- 20 秒仍无人开始：强制开始（forced），不再无限等待；
- 单观众房间：该观众 ready 即开始，不空等。
- 客户端准备失败或上报 `visible: false`（后台标签页）会回报服务端，并把该观众移出本轮；后台标签页在回合开始时也会主动上报一次，不再让其他观众白等 8 秒；
- 准备轮次的 `ready` 与 `eligible` 只用于同步，不跨重启持久化；恢复房间仍保持暂停。
- `ott_playback_start_total{result,service}` 记录 all-ready / partial / forced 的实际开始方式。

开始播放后，新加入或刚换源的客户端有 **8 秒初始同步冷却**：冷却期内漂移小于 10 秒不硬跳，
只允许速率追赶；冷却结束后恢复 3 秒硬跳阈值。正在缓冲或缓冲前瞻低于 1.5 秒时禁止自动硬跳，
避免“seek → 丢缓冲 → 再 seek”的死亡螺旋。

这组参数是工程起点，不是实测最优值；跑道、8 秒等待和 20 秒硬兜底需要按真机与源类型继续标定。

未知时长的 Direct / HLS / DASH 点播仍创建首帧准备轮次，不因 `length` 缺失提前启动房间时钟。
准备回执现在可带 `durationSeconds`：服务端只在当前源仍没有可用长度、且回执属于本轮源时填充
`currentSource.length`，随后沿用正常的片尾检测自动下一项。没有准备轮次的播放路径仍可能带着
未知长度运行，属于剩余覆盖缺口。
只有明确标记 `isLive` 的直播跳过 VOD 准备；Node 自定义清单与 Edge 清单均保留 live 标记。
鉴权与加入在途时，单次 ready / status 回执等待成员建立后处理；断开后旧操作停止，密码校验的异步结果也重核连接。

片尾 30 秒的“下一集预取”只预热 DNS/TLS 与清单/首个 Range，不创建播放器、不参与 ready 上报；
换源或队列长度变化时会中止仍在途的预取；当前播放器正在缓冲或缓冲前瞻低于 5 秒时也不预取，
避免它和首帧加载、缓冲跑道抢带宽。

直播 HLS（清单没有 `#EXT-X-ENDLIST`）单独标记为 `isLive`：不进入 VOD 首帧准备，不按窗口时长
判播完；客户端同步引擎看到 live 后不再按 VOD 房间时钟硬跳，由 HLS 自己维持 live edge。这解决
“直播被当点播、窗口时长后被出队/反复回跳”的问题；直播不追求帧级同步。

## 本机速率微调（现行实现）

Direct（MP4 / 原生 HLS）、Hls（hls.js）和 Dash 播放器在播放中自动修正中等漂移。
本机落后时稍微加速，超前时稍微减速；该倍率乘在房间速度上，不改变房间设置、进度条或倍速菜单。
YouTube、PeerTube 仅支持离散倍速，Vimeo 没有对应 setter，三者明确不启用微调。周期 tick 与收到房间 sync 的纠偏入口现在共用同一套被动策略（`passiveSeekLimit`）：可微调且播放中仍为 3 秒；没有微调时，原生播放器使用 300 ms 死区，嵌入式播放器（YouTube / Vimeo / PeerTube / Bilibili，seek 是 API 重载或估算）保留 1 秒死区。Bilibili 官方 iframe 缺少控制 API，只能重载和估算位置，不属于精确 seek。
能力由播放器显式声明，与倍速菜单提供几个选项无关。

当前工程起点如下，尚未完成低端安卓真机标定，不能视作行业标准或实测最优参数：

| 参数                 | 当前值                                           | 用途                                     |
| -------------------- | ------------------------------------------------ | ---------------------------------------- |
| 开始 / 停止微调      | 300 / 150 ms                                     | 迟滞避免在阈值附近反复启停               |
| 漂移 ≤1 s            | 8%                                               | 1 s 以内使用 8% 上限；1–3 s 线性增至 15% |
| 最小微调上限         | 房间速度的 ±8%                                   | 浏览器保持默认音调保护                   |
| 追赶上限             | 漂移 1 s 起线性增大，3 s 时到 ±15%               | 秒级漂移优先追赶而不是跳帧               |
| 周期 tick 硬跳阈值 | 可微调且播放中 3 s；初始 8 s 冷却期间 10 s；不可微调 / 关闭开关时：原生 300 ms，嵌入式 1 s | 周期观察的被动纠偏 |
| 收到 sync 的纠偏阈值 | 可微调且播放中 3 s；不可微调 / 关闭开关时：原生 300 ms，嵌入式 1 s | `seekIfDriftIsLarge` 路径，与 tick 共用 `passiveSeekLimit` |
| 房间暂停时的对齐 | 原生 40 ms（约一帧），不受硬跳冷却限制，同一暂停位置只纠正一次；嵌入式 1 s | 见下文“暂停落在同一帧” |
| 微调截止时间         | max(8 s, 收敛所需 × 1.25)，上限 30 s             | 未收敛则恢复房间速度并硬跳一次           |
| 同一方向只写一次速率 | 方向或追赶上限变化时才重写                       | 避免每 250 ms 重定时造成音频卡顿         |

Syncplay 的固定 0.95× 与进入 / 退出迟滞可作为机制参考，详见
[竞品源码对照](watch-party-comparison-2026-11-17.zh-CN.md)。本项目的 ±15% 是工程取舍，
尚未通过多设备主观听测确定最优值。YouTube、PeerTube、Vimeo 不启用微调，硬跳依上面的两个入口处理。漂移在微调期间变大时，截止时间会按新的
追赶量延长，避免“按小漂移算出 8 秒”过早放弃。

位置观察与硬跳节流分开：硬跳仍有 2 秒 / 缓冲后 8 秒间隔，间隔中允许微调。
暂停、播放准备握手、拖动、恢复、自动播放受阻、换源、销毁以及临时 2× 手势都会取消微调。
房间倍速变化会恢复新基准并使旧速率记录失效，下一拍才能重新叠加。原生 setter 同时维护恢复
快照，微调不会直接改共享 UI 倍速 ref，也不会绕开 setter 直接改 video 元素。

## 细纠偏带（60–300 ms）

300 ms 以下原先完全不纠正，每位观众可以长期停在房间时钟 ±300 ms 内，上面的速率弯曲停在
150 ms 之后也把这段残差永久留下。现在这一段由细纠偏带处理，条件与速率弯曲相同（播放中、
播放器声明可微调、开关开启、没有临时 2×）：

| 参数 | 当前值 | 说明 |
| --- | --- | --- |
| 进入 / 退出 | 60 / 20 ms | 进入要求当前读数**和**最近连续三次观测的中位数都达到 60 ms，单次抖动不触发 |
| 速率偏移 | `漂移 / 4`，夹在 0.5%–2% | 按 0.5% 一档量化，只有档位变化才重写 `playbackRate` |
| 音调 | `preservesPitch = false` | 仅在房间速度恰为 1× 时启用；结束、被打断或交给速率弯曲时恢复 |
| 截止 / 回退 | 无 | 漂移涨到 300 ms 即交给速率弯曲；弯曲停在 150 ms 后由本带接手余量 |

用重采样而不是保持音调的时间伸缩，依据是 Chromium 媒体代码自己的说明：WSOLA 在接近 1.0 的
速率下会产生可闻的 warbling / stuttering，重采样没有失真但会变调（2% 约 1/3 个半音）。
浏览器不支持 `preservesPitch`、或房间速度不是 1× 时，细纠偏带整体不启用，行为与此前相同。
细纠偏的时长计入 `ott_playback_bend_seconds`，速率写入计入 `rateWrites`。
细纠偏或速率弯曲结束时恢复的是房间**当前**的倍速，而不是它开始时的倍速：结束它们的常常正是
一次倍速变化（临时 2×、倍速菜单），播放器此时已经应用了新倍速。

**这组数值没有做过听测。** 逻辑有单元测试覆盖；60 / 20 ms、2% 上限、是否在音乐类内容上可闻，
以及 Firefox / Safari 在 `preservesPitch = false` 下的实际表现，都需要真机确认。观众关闭
“速率弯曲”开关即一并关闭本带。

## 硬跳的预测定位

房间播放中的硬跳原先以“此刻的房间位置”为目标，播放器取数据、解码、恢复播放期间房间时钟
继续走，于是每次加入、拖动或大漂移硬跳之后都落后恰好这段耗时，再靠 8%–15% 的弯曲追十几秒。
现在目标是 `房间位置 + 预计耗时 × 房间速度`，适用于播放中的房间、原生播放器、非直播；房间
暂停、嵌入式播放器、直播不加提前量。

- 两个估计值：`reset()` 之后第一次硬跳（冷加载）初值 0.5 秒，其余硬跳初值 0.3 秒，范围 0–3 秒。
  初值偏保守：估高了本机会超前，只能靠减速收回；估低了只是和以前一样落后。
  换源不清空估计值，只把下一次硬跳重新标为冷加载。
- 估计值用结果修正而不是秒表：硬跳之后第一次有效观测到的漂移就是预测误差（正值表示仍落后，
  耗时被低估），`估计 += 0.5 × 漂移 ÷ 房间速度`，每次硬跳只修正一次。房间暂停、`reset()`、更新的
  硬跳会丢弃这次待修正。
- 房间速度取房间自身的倍速，与本机是否开启速率弯曲无关。
- 目标不超过片尾（或裁剪终点）：越界的目标会被元素钳到片尾，原生 seek 的保持条件随之永远不
  满足。`media-seek` 自身也把目标钳在媒体时长之内。被钳住的硬跳不参与估计值修正。
- 预测过头（本机超前）或不足的余量由速率弯曲和细纠偏带收敛。
- 当前估计值可在 `getMetrics()` 的 `seekLeadSeconds` / `loadLeadSeconds` 读到，不上报服务端。

初值同样是工程起点；每台设备会在头几次硬跳内收敛到自己的耗时。

## 缓冲期间暂停纠偏

元素正在缓冲时漂移观察与速率写入一并暂停：停住的播放器测不出有意义的漂移，为它写入的速率
只会在恢复播放的瞬间原样带进追赶。缓冲结束后的 8 秒内不硬跳（沿用原有的缓冲冷却），之后恢复
常规纠偏；恢复瞬间按常规路径处理——能微调的用速率追赶，超过阈值才跳。

显式的拖动与房间指令不受影响：它们先于漂移观察执行，缓冲中的设备照样跟随房间的跳转。
服务端现在为每次显式 seek 分配单调 `seekId`；客户端看到新的 id 会直接硬定位，而普通位置 sync
仍走 `tolerateSmallDrift` 的被动纠偏。这样短距离拖动不会被本地变速悄悄吸收。

`media-seek` 的硬 seek 死区从 50 ms 调整为 250 ms：播放中的元素即使只差 0.1 s，也会被 pause + `currentTime` 触发一次音频管线清空，听起来就是开头的停顿。250 ms 与首帧准备和恢复快照的容差一致，低于它的误差不会被当作“用户跳转”。

## 暂停落在同一帧

房间暂停时，原生播放器（Direct / HLS / DASH）先应用暂停，再把元素对齐到房间的暂停位置，容差
40 ms（约一帧）。已暂停的元素没有在跑的音频管线，seek 没有可闻代价，所以这一步不等 2 s / 8 s
的硬跳冷却；`media-seek` 对已暂停元素的容差相应是 20 ms，播放中仍是 250 ms。同一个暂停位置只
纠正一次：只能落在关键帧上的播放器不会被反复 seek。正在缓冲的设备、直播、嵌入式播放器和
进行中的首帧准备不走这条路径。此前各端停在自己元素恰好所在的位置，彼此可相差 0.3 s 以上。

## 时钟锚点与起始位置

客户端只在 sync 带有 `playbackPosition`、或片源身份（`service` + `id`）变化时重置时钟锚点。
只改字幕、补时长这类同一视频的元数据更新不再重锚；此前这类消息会让每位观众回到各自上一次
锚定的位置。服务端在 `currentSource`、`isPlaying` 或 `playbackSpeed` 变化时，同一条消息里一并
带上当时的位置，因此“恢复播放”也不再依赖客户端保留的旧位置。

HLS 的起始位置通过 hls.js 配置项 `startPosition` 传入：清单解析前调用的 `startLoad(pos)` 只会
置位强制启动标记，位置参数被丢弃，随后按 `config.startPosition` 启动（hls.js 1.6.12，有真实库
回归用例）。DASH 用 `initialize` 的第四个参数。直播源不传起始位置，由播放器自己维持 live edge。

临时房的 Redis 快照把位置与锚点写成同一时刻；恢复仍在播放的临时房时在加载瞬间重新锚定，
进程停机的时间不计入进度。此前快照写入实时位置却保留上一次暂停 / 拖动的锚点，恢复后进度
会多算一遍这段时长。

## 速率弯曲开关（按设备保存）

速率弯曲默认在所有设备开启。开关是普通用户偏好，写入 `localStorage["settings"]` 的
`rateBendEnabled`，因此每台设备/浏览器各自独立，刷新或重新进入房间后保持；关闭后同步只做
硬跳纠偏，周期 tick 与收到 sync 共用同一策略：原生播放器 300 ms 死区，嵌入式播放器 1 s
（其 seek 是重载或估算）。没有按 UA 或机型分默认值：是否适合弯曲由当前设备的实际观感决定，
观众关掉一次即可在该设备长期生效。

## 房间时钟的锚定（时间戳，现行实现）

带位置的 `sync` 现在同时带 `serverTime`：服务端采样该位置那一刻的 `Date.now()`（`Room.playbackClock()`
一次取出位置与时刻）。显式 seek 只弄脏位置本身，同样带时间戳。探测回复 `pong` 也带 `serverTime`。两个字段都是可选的，Edge 预览后端不发，
客户端收不到时走下一节的旧路径。

客户端用探测往返估计本机时钟与服务端时钟的偏移（`connection-latency.ts`）：

- 往返时长用 `performance.now()` 量；偏移 = `serverTime −（收到时刻 − 往返 / 2）`。
- 取最近样本（最多 8 个，每个样本各自 3 分钟过期）里**往返最小**的那个的偏移。
- 加入后第一个带 `serverTime` 的回复触发 3 次间隔约 250 ms 的连续探测，之后回到 15 秒一次；标签页
  回到前台也补一次。服务端的探测回复改为容量 5、每秒补 1 个的令牌桶。连续探测不计入“半开连接”
  判定，旧服务端丢弃它们不会让客户端误判断线。
- 每次重连清空样本。
- 本机映射以 `Date.now()` 为基准。`Date.now() − performance.now()` 相对最新样本变化超过 200 ms
  （系统校时、休眠）时丢弃样本并立即重测。重测完成前**不报告偏移**（回到下一节的到达时刻锚定），
  并把这段时间标记为“时钟不可信”（最长 5 秒）：同步引擎在此期间不纠偏、不硬跳，已挂起的本地
  起播定时器取消。校时与休眠在本机无法区分，而两者需要相反的修正——校时后旧偏移错了整个步长，
  单调时钟会停走的平台（Windows 以外）休眠后旧偏移仍然正确——所以两种猜测都不做。
- 全部样本过期（3 分钟内没有任何探测回复）同样不报告偏移。

锚点 = `serverTime − 偏移`，与这条消息何时被读到无关：消息在重传或主线程繁忙后面晚到多少，都
不再变成锚点误差。加入时最初几条 sync 先于第一个 `pong` 到达，此时先按旧路径锚定，偏移一到
就按记下的 `serverTime` 重算（`REANCHOR_FROM_SERVER_CLOCK`）。剩余误差的下限是上下行延迟差的
一半，没有外部时钟无法测出。

多人起播的 `playbackPreparation.startAt` 现在由客户端本地执行：已回执（`waiting-ack`）且偏移已知
的观众在 `startAt − 偏移` 这一刻自己开始播放并解除准备静音，随后到达的 `isPlaying: true` 只作
确认，不再触发暂停或 seek。本轮被替换 / 取消，或起播后 3 秒内没有等到确认，本地起播即撤回。
每一轮只尝试一次本地起播：撤回之后 `startAt` 已经过去，再次挂起会立即触发，本机就会在本轮
每次被重新发布或每个时钟样本到达时独自带声音起播一次。
偏移未知、旧服务端、未回执的观众仍然在收到 `isPlaying` 时起播。提前量仍是固定 1 秒。

## 消息在途补偿（无 `serverTime` 时的回退路径）

同步消息描述的是它**离开服务器那一刻**的房间时钟。客户端若按“收到时间”重新锚定
`playbackStartTime`，就会带着一个固定的单向延迟落后于房间（同步 ping 每 15 秒一次，
取最近 8 个往返样本的**最小值**的一半作为单向延迟，样本超过 3 分钟视为过期而不使用）。
锚点因此写成 `收到时间 − 单向延迟`，与 Syncplay 的 forward-delay 补偿同一思路。
RTT 样本来自应用层 `{action:"ping"}` / `{action:"pong"}` 往返；服务器每秒最多回一次。

这里的“8% 追 500 ms 需要 6.25 秒”只是恒定速差的算术估计；实际算法在同一方向保持速率，
直到漂移进入 150 ms 停止死区，因此不会每拍减速。8 秒回退是最坏情况兜底，需结合实际
出帧和缓冲观察。

## 漂移分布度量

`maxDrift` 只有一个最大值，分不清“全程偏 20 ms”和“全程偏 280 ms”。同步引擎现在按时间加权
累计 |漂移| 落在 `[0, 40 ms)`、`[40, 80)`、`[80, 150)`、`[150, 300)`、`[300 ms, 1 s)`、`≥1 s`
六档的秒数，以及处于速率弯曲状态的秒数；只统计房间播放中、相邻两个 tick 都完成观测的区间，
单步上限 1 秒，暂停、缓冲、seek 和后台节流造成的空档不计。随质量上报进入
`ott_playback_drift_seconds{service,bucket}` 与 `ott_playback_bend_seconds{service}`，
`bucket` 标签由服务端固定生成。漂移仍是相对本机估计的房间时钟，不是观众两两之间的偏差。

## 2026-10-21 开头音频卡顿

现象：直链 MP4 开始播放的前几秒，声音反复“播一下、顿一下”，画面不一定停。

启动探针记录到两个独立原因：

1. `playback-sync` 在追赶时每个 tick（250 ms）按漂移重算一次速率，`playbackRate` 被连续
   重写。浏览器每次写速率都会重新安排音频时间伸缩，听感就是连续微顿。现在同一方向只写
   一次，保持到漂移进入 150 ms 停止死区；只有方向或追赶上限变化时才重写。
2. `media-recovery.restoreMetadata()` 在元数据到达时按快照位置 seek。新片源的快照接近 0，
   但元素此时已经自己播了约 0.1 s；这次“暂停 → seek 回 0 → 再播”会清空音频管线。现在
   快照位置本身接近 0、且当前播放位置与目标相差不超过 0.25 s 时不再 seek；真实的恢复
   位置仍然恢复。

验证：同一条 `oceans.mp4` 的启动事件从 `play → pause → seeking → seeked → play` 变为
`play → loadedmetadata → loadeddata → canplay → playing`，速率保持 1.0；`media-recovery`
与 `playback-sync` 单测覆盖这两个回归。

2026-09-15 复核：曾按竞品做法尝试“每设备输出偏移滑块”（本机目标位置 = 房间位置 − 偏移）。

绘制、与增强层/PiP/全屏需要额外协调，因此仍按上面的要求等实测数据再评估。
