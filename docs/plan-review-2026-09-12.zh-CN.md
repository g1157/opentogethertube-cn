# 2026-09-12 计划复核与方向结论

本轮按 `warm-discovering-kazoo.md` 的四项决定实施：原生播放器速率微调、缓冲时一起暂停
默认关闭、蓝牙改为测量任务，以及最小安全响应头和报告模式 CSP。

## 实施时修正的细节

- 原生播放器通过显式能力声明启用微调。倍速菜单有多个档位，不代表支持连续小数速率。
  YouTube、PeerTube、Vimeo 仍走既有纠偏路径；不把它们宣传为已获得中等漂移微调。
- 300 / 150 ms、±8% 和 8 秒是工程起点。目前没有低端安卓十分钟测量结果，不能声称
  参数已经完成标定，也不能将恒定速差的算术估计当成实际收敛时间。
- 缓冲门控必须在房间已经被自动暂停时继续检查；照抄“房间没在播就 return”会无法释放。
  手动暂停必须撤销自动恢复权；超时和显式继续播放都需要冷却，避免连续接管。
- 原有 Vuex 订阅在 mutation 之后比较新状态和 payload，实际会吞掉所有播放状态上报。
  本轮改为报告去重，并在转入后台时主动清除旧的 buffering，单纯不再发送会留下旧等待方。
- 迁移使用实际表名 `Rooms`。旧服务端没有 `bufferGateMode` 时，完整房间同步按 `off`
  重置，避免从上一房间带入状态；Cloudflare 预览隐藏尚未实现的设置。
- `opentogethertube-next` 持有主仓库 `.git`，只能对齐，不能删除。旧分支先推到 GitHub
  备份；过时文档改动也另存补丁，再对齐检出。
- 原计划“关标签页验证 15 秒上限”混合了两种情况：正常离开应立即移除等待方；15 秒
  上限要用仍保持连接但持续缓冲的观众验证。这两条分别验收。

## 蓝牙：不做整体时间轴偏移滑块

一起平移声音和画面的播放位置，不能消除二者的相对输出延迟，还会移动画面与房间时钟的
关系。浏览器、系统和耳机可能已有不同程度的补偿，不能从理论延迟直接推出用户实际听到的
音画差。先用同一唇形测试片，对比全新页面的元素直出与 WebAudio 增强路径。

当前实现把增强调回 100% 后不会拆除已经建立的媒体源图。因此仅切换数值并不能形成干净
的 A/B 对照。`outputLatency` 和 `baseLatency` 是辅助观测值，额外加一个音频 DelayNode
也不会解决原本声音已经滞后的问题。测量模板和未完成项见 [播放同步与测量记录](playback-sync.zh-CN.md)。

## 语音：本阶段不内置

决定基于新增范围与验证成本：麦克风授权、拒绝后的恢复、回声处理、媒体与语音的音频焦点、
移动端中断、蓝牙切换、ICE 重启、重连和 TURN 运营，都需要独立设计。现有 WebSocket
可以承载信令，媒体连接仍是独立生命周期。若未来需要可靠连接，应评估和测量 TURN 回退，
不能以“P2P mesh”推导服务器带宽恒为零。

原计划给出的 NAT 成功率、协议开销、带宽数值和特定云安全组默认规则缺少本项目的实测
或可追溯依据，不作为容量规划结论。CGNAT 本身不等于一定不能直连；需要测试实际网络
组合。TURN 端口段可以配置，也不是所有部署都必须开放同一整段端口。

原计划关于法律性质、判例和站外语音必然不改变责任边界的表述不足以作为法律结论。
公开发现、内容处理、服务地区和运营方式需要具体评估；仅使用 P2P 或不录制也不能自动
推出免责。本轮不增加语音入口或麦克风授权流程。后续是否提供站外入口另行做产品决定。

## 弹幕：Phase 2，锚定视频时间

聊天用于当下交流；弹幕需要同时绑定片源身份和播放位置，重看该片段时能够重新呈现。
单纯让现有聊天浮起来不能提供这种能力。服务端应确定时间锚点，同一条消息可在聊天列表
保留时间徽章，并由独立的播放器覆盖层按时间安排轨道。

后续设计至少包括消息 ID / 去重、片源变化、拖动与倍速后的重新调度、存储与保留期限、
权限与发送频率限制、字幕和手势层冲突、可读性及本地关闭选项。不能把工作量简化为
“服务端多一个字段、客户端几百行”。本轮只交付结论，不提前加入未验证的弹幕实现。

## 运维范围

正式升级先备份配置、数据库和 Redis，再使用已发布镜像及对应迁移。清理只涉及计划中
列出的旧 OTT 容器和目录，保留数据卷、现网配置、旧实例最后一份配置及全部 SQL 备份。
其他服务器应用不在本轮范围。DNS / IPv6 不变；AAAA 答复顺序本身也不是可靠的连接故障
修复方案。实际执行结果、版本和限制在发布验证记录中登记。
