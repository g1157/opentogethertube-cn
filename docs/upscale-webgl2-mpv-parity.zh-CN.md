# WebGL2 极致档与 mpv A+A (HQ) 的逐块对齐（2026-09-29）

「AI 超分（极致）」的目标是：**在没有 WebGPU 的设备上，跑 mpv 的同一条 A+A (HQ) 链**。
本文记录把它对齐到 mpv 参考帧的过程与结论——链路语义（MAIN / 命名纹理 / 翻转 / 每段放大
闸门）到底怎么对应、修掉了哪三个真问题、以及逐段实测的一致性数据。

## 结论速览

1. **mpv 的链路模型是「MAIN 是此刻的画面」**：文件按顺序执行，一个文件只写自己的命名纹理时，
   画面不动（`Restore_CNN_VL` 的 16 个卷积 pass 都是这样）；写 `MAIN`（或完全不写 `//!SAVE`）
   的那一个 pass 才替换画面（每个修复/放大文件的最后一个 pass）。因此"段输入"这个概念只在
   驱动内部成立，转换器要按**运行到该 pass 时画面是否还是视频纹理**来决定读取是否翻转。
2. **放大闸门是逐文件的**，不是全局一个开关：每个放大文件自带
   `//!WHEN OUTPUT > 1.2× MAIN`。2× 目标下，第一段 x2（VL）跑完之后 MAIN 已经等于目标尺寸，
   第二段 x2（M）自己的闸门为假——mpv 在 2× 目标下实际只跑 **46 个 pass**（模块里是 55 个）。
3. **`Clamp_Highlights` 的 clamp 必须挂在链尾**。它由三段组成：两段统计挂 `MAIN`
   （必须看到未处理的画面），第三段 clamp 挂 `PREKERNEL`（mpv 的 hook 顺序里在全部 `MAIN`
   之后）。统计放在链首、clamp 放在链尾，才是官方文档说的那个语义；整组放在链首时
   `min(current, statsmax)` 恒等于 `current`，等于空转（镜像里的 WebGPU 库就是这么摆的）。
4. **与 mpv 参考帧的一致性**（细节 = 3×3 高通后的相关系数）：

   | 对比（同一片源、同一帧 t=60s） | 平均绝对差 | 相关系数 | 细节相关 |
   | --- | --- | --- | --- |
   | 两边的源帧（mpv `off` vs 浏览器 video） | 0.164 / 255 | 0.99997 | 0.9995 |
   | `Restore_CNN_M` 单文件（1×） | 0.501 | 0.99885 | 0.9807 |
   | `Restore_CNN_VL` 单文件（1×，成对特征图 + 15 纹理合并层） | 0.407 | 0.99932 | 0.9872 |
   | 修复栈 `VL + M`（1×） | 0.589 | 0.99818 | 0.9744 |
   | **整链 A+A (HQ)（1×）** | **0.579** | **0.99827** | **0.9750** |
   | **整链 A+A (HQ)（2×）** | **0.762** | **0.99404** | **0.9295** |
   | **S 档 `Restore_S + Upscale_x2_S`（2×）** | **0.647** | **0.99556** | **0.9433** |
   | GPU 上的 STATSMAX vs 源帧 5×5 最大值（逐像素） | 0.025 | 0.99999 | 0.9999 |

   2× 那行的差距主要来自 mpv 截图侧的缩放：`screenshot video` 固定输出视频原生分辨率，
   放大后的画面会被它的缩放器缩回 1080p，而浏览器侧是 2×2 盒式降采样对齐（两者不是同一个
   滤波器）。1× 的数据没有这一步。

5. **性能**（macOS、Firefox 142 headless，1080p 源）：55 段着色器首次编译约 **0.29s**；
   1080p→2× 时极致档 46 个 pass 跑 **12.3 fps**，S 档 22 fps。极致档的帧率门槛（≥24fps@4060）
   需要在维护者的 Windows 机器上复测。

   缓冲的占用也是这一轮修掉的：链路里每个用过的中间纹理都会分到一块渲染目标，2× 下就是十几个
   1× 加好几块 2×（16F，合计数百 MB）。现在规划器会算出每块缓冲"最后一次被渲染或被采样"的
   那一步，驱动在那里立刻释放；只有 present 要画的那张画面留到帧末。输出逐像素不变。

## 方法：mpv 参考帧是怎么拿到的

- 目标是维护者自己的那条链（mpv.net 菜单 CTRL+7 =
  `Clamp_Highlights; Restore_CNN_VL; Upscale_CNN_x2_VL; Restore_CNN_M; AutoDownscalePre_x2;
  AutoDownscalePre_x4; Upscale_CNN_x2_M`），片源是同一集动画的 1080p 直链，t=60s。
- 在非交互的 SSH 会话里，`--gpu-context=d3d11` 无法创建 swapchain（`0x887A0022`，
  虚拟桌面上拿不到），改用 `--gpu-context=win`（WGL）出画；`--no-config` 保证不受
  mpv.net 配置影响。
- 那个会话的"屏幕"只有 1024×576，`--window-scale=2` 也会被压回去，`OUTPUT` 永远够不到
  1.2×，放大段不会运行。解决办法是**只把放大文件的 `//!WHEN` 行去掉**（其余一字不改）：
  这样 VL 放大段会在小窗口下照常运行，而 M 放大段仍被它自己的闸门排除——这与真实 2× 目标
  下的行为完全一致（那里 M 放大段同样被排除）。
- 截图用 `screenshot video`，它输出的是**视频原生分辨率**的画面（shader 放大后再缩回去），
  所以 2× 对比是"浏览器的 2× 输出盒式降到 1080p"对"mpv 的 2× 输出由它自己缩放回 1080p"。
- 浏览器侧用同一片源、同一帧：`video.currentTime = 60` → 等 `seeked` → 暂停 → 截图。
  **测量之前不要播视频测帧率**：播完再 seek 回 60s 不保证拿到同一帧，这一条浪费过一整轮排查
  （症状是"两幅图细节相关只有 0.45、处处块状差异"，最后发现是 t≈63s 对 t=60s）。

## 修掉的三个问题（症状 → 根因 → 修法）

1. **输出近全黑、只剩很淡的轮廓**（S 档梯度 1.37 对源 4.13）。
   根因：段输入缓冲没有纳入 slot 分配器的活跃期——`Restore` 段的输出放在某个槽位，`Upscale`
   段中途复用同一槽位，导致 depth-to-space 的"加回画面"读到的是最后一张特征图。
   修法：规划器把每段输入当作一个"名字"参与活跃期分析，并预留当前画面所在的槽位；
   配套单测（"绝不在画面所在的缓冲上渲染"）。
2. **2× 目标下第二段 x2 也在跑**（55 段全跑、算到 4× 再降采样，fps 8.7）。
   根因：移植版用一个全局 `magnifying` 判断，而 mpv 是每个文件按**当时的画面尺寸**判断。
   修法：`planChain` 逐段计算闸门；2× 下实际 46 段，fps 回到 12.3。
3. **`Clamp_Highlights` 整组放在链首**（clamp 在链首等于空转，画面上的振铃没被处理）。
   根因：一是位置，二是转换器按"文件序号是否为 0"决定读取翻转——统计文件不写画面，它后面
   的第一个文件读到的仍然是视频纹理，却按"非首个文件"关掉了翻转，整幅画上下颠倒。
   修法：生成脚本把该文件拆成"统计"和"clamp"两个文件（统计在链首、clamp 在链尾），
   转换器改为跟踪"画面是否还是视频"来决定翻转。

## 复现

- 重新生成两个模块：`scripts/anime4k-glsl-to-webgl2.sh <官方 v4.0.1 GLSL 目录>`
  （该脚本负责把 `Clamp_Highlights` 拆成统计/clamp 两份再喂给转换器）。
- 单测：`yarn workspace ott-client vitest run tests/unit/upscale-anime4k-webgl.spec.ts`
  （覆盖闸门、MAIN 的推进、缓冲活跃期、"画面所在槽位"四条规则）。
- mpv 参考帧：`mpv.exe --no-config --vo=gpu --gpu-context=win --gpu-api=opengl
  --glsl-shaders=<链> --screenshot-directory=<目录> --script=<定点截图脚本>`。
