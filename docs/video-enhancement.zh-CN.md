# 画质增强与渲染倍率

播放器设置里的“画质增强”提供五个档位、加关闭共六个：关闭、清晰化、影视（去噪去带，真人剧集与电影用）、
AI 超分（Anime4K）、AI 超分（质量）、AI 超分（极致）。**六档在所有设备上都列出**——选哪档都有效：
AI 三档优先走 WebGPU，拿不到 WebGPU 时自动改用 WebGL2 跑同一套 Anime4K 网络（链路更重，见下文）。
清晰化档把视频帧渲染到一张画布上再放大显示，因此“渲染倍率”决定画布有多少像素；
本次改动调整了自动倍率的规则，并把清晰化档的放大换成了边缘自适应放大，同时给 AI 超分
增加了一个更重的预设。

播放器设置里的「画质增强」把档位排成一行横向切换，下面固定是「进阶」区：锐化强度、渲染倍率、
自动降档。标题旁的 ⓘ 悬浮（触屏点击）弹出说明，就地讲清每档的作用与代价（与本文内容一致）。

## 渲染倍率与尺寸规则

| 档位 | 行为 |
| --- | --- |
| 自动 | 按显示尺寸计算 `min(框宽×dpr ÷ 源宽, 框高×dpr ÷ 源高)` 作为下界；指针设备（鼠标）再抬到至少 2× 源，触屏设备保持贴合显示框；随后限制在 1×–3× 与像素预算内 |
| 0.25×–3× | 按所选倍数渲染，不看显示尺寸；可高于或低于自动值 |

自动档有三条硬边界：

-   **不低于源分辨率。** 着色器的放大与缩小只用一次双线性采样，而浏览器缩小未经处理的原片
    用的是多抽头滤波，画布低于源分辨率时增强后的画面反而比原画更软。手机上 1080p 视频
    的显示区域通常只有 780×438 设备像素，旧规则会渲染 0.41× 的画布，本次修复的正是这种情况。
-   **指针设备至少 2× 源。** Anime4K 的预设只有在目标明显大于源（库内判定 >1.2×）时才跑
    Upscale 阶段，设计点是 2× 上采样后由显示端下采样；把画布钉在显示框上会让最高档只剩
    Restore 阶段，画质与 GPU 占用同时下降。触屏设备（`pointer: coarse`）继续贴合显示框，
    因为多出来的像素只换来发热与耗电，自动降档阶梯仍是兜底。
-   **像素预算 3840×2160。** 源远高于显示尺寸时（例如手机上放 8K），自动档最多渲染 4K
    等量的像素，不会为看不出差别的画面渲染上千万像素。预算同时是 2× 目标的上限：
    1080p 源正好 2×（3840×2160），1440p 源落到 1.5×，4K 源不放大。

设备像素比上限为 3（`MAX_DPR`），三处（渲染、详情面板、队列预览）一致。

显式档位不受预算约束，只受 3× 上限约束；自动降档写入的 0.25×–0.75× 档同样保留，
它们是在设备吃不消时低于源分辨率的明确取舍。

## 清晰化档的管线

放大时走两遍，顺序与 AMD FSR 1 的建议一致：

1. **EASU**（Edge Adaptive Spatial Upsampling，移植自 AMD FidelityFX Super Resolution 1.0，
   MIT 许可，许可证随 `client/src/util/upscale/cas.ts` 保留）把源帧按显示倍率做方向自适应的
   Lanczos 近似放大，并用最近 2×2 纹素限制输出，避免负瓣产生振铃；
2. **CAS** 在输出分辨率上做邻域钳制的锐化，滑块强度作用于放大后的画面。

画布不大于源分辨率时（自动档的 1×、显式低倍率）保持单遍 CAS：这种场景不需要放大，
浏览器负责最终缩小，锐化仍按源纹素计算。

Anime4K 档不经过这条管线，它把画布尺寸交给 WebGPU CNN 作为目标尺寸，因此渲染倍率
同样对它生效（档位切换会重建管线）。进入或退出全屏、改变窗口尺寸后，它也会按新的显示尺寸
重建一次：管线的目标尺寸在构建时就固定了，不重建的话画布会停在旧分辨率被浏览器拉伸，
全屏下白白损失解析度。为避免拖动窗口时反复重建，尺寸稳定约 0.25 秒后才动手。

## AI 超分：快速与质量两档

两档都来自 `anime4k-webgpu`（Anime4K 的 WebGPU 移植，MIT），都需要 WebGPU：

-   **AI 超分（Anime4K）** 使用官方预设 Mode A，实测在 720p → 2K 目标下为 **3 个 pass**；
-   **AI 超分（质量）** 使用官方预设 A+A（`Restore → Upscale → Restore → Upscale`），
    实测为 **4 个 pass**，且第二段修复运行在已经放大的分辨率上，同样面积的 pass 像素数是
    第一段的 4 倍，因此整体开销明显高于“4/3”这个字面比例，实际约为快速档的两倍。

自动降档的顺序为：质量 → 快速 → 清晰化 → 逐级降倍率 → 关闭。质量档无法启动时（例如设备
内存不足）只退回快速档，并提示“已切换为「AI 超分」”；快速档无法启动才退回清晰化。

### 没有 WebGPU 时走 WebGL2（2026-09-29 起）

「AI 超分」两档不再要求 WebGPU：优先用 WebGPU 的移植库，拿不到设备或管线创建失败时，
自动改用 WebGL2 跑**同一套 Anime4K 网络**（官方 GLSL 的 S 档，`Restore_CNN_S` 4 个 pass +
`Upscale_CNN_x2_S` 5 个 pass，最后一段 depth-to-space 才是 2× 放大）。这条路径覆盖了
Windows 之外的 Firefox（`requestAdapter()` 会直接抛错）、Safari 26 之前、以及被驱动黑名单
挡住的机器；质量档在没有 WebGPU 时与快速档共用这条链路。

着色器由 `scripts/anime4k-glsl-to-webgl2.mjs` 从官方 v4.0.1 GLSL 生成（权重逐字不变，
只把 mpv 的 `//!HOOK` 宏改写成 uniform 与固定 pass），生成结果在
`client/src/util/upscale/anime4k-glsl.ts`，驱动在 `anime4k-webgl.ts`。实测（Firefox 142 与
Chromium 141，同一画面暂停后对比同一显示尺寸下的平均梯度）：画布 53.6 / 53.9，原画
39.7 / 39.9，即增强输出比原画锐约 35%。

可用性判断用一次真实的适配器请求（`util/upscale/webgpu-probe.ts`），而不是
`"gpu" in navigator`：后者在 Firefox 上恒为真，会让用户在下载完 3.4MB 的 WebGPU 库之后才
失败；探针拿不到适配器就直接走 WebGL2，且失败结果不缓存（换档、换片可再试）。


### 极致档（WebGL2 上的 A+A (HQ)）

WebGPU 可用时，「AI 超分（质量）」就是 mpv 的 A+A (HQ) 同款链（`ClampHighlights → CNNVL →
CNNx2VL → CNNM → CNNx2M`）。拿不到 WebGPU 的设备（Windows 之外的 Firefox 等）也有同一条链：
`util/upscale/anime4k-ultra.ts` 用通用多 pass 驱动跑官方 v4.0.1 的
`Clamp_Highlights`（统计挂在链首、clamp 挂在链尾，与 mpv 的 `PREKERNEL` 一致）+
`Restore_CNN_VL + Upscale_CNN_x2_VL + Restore_CNN_M + Upscale_CNN_x2_M`，模块里共 55 个 pass，
权重逐字来自官方 GLSL（`anime4k-ultra-glsl.ts`，约 390KB，懒加载）。放大段按每个文件自己的
`//!WHEN` 闸门逐段判断：2× 目标下第二段 x2 与 `AutoDownscalePre` 都不运行，实际每帧
**46 个 pass**。缓冲按"名字的活跃期"复用，并在最后一次使用后立即交还给驱动，所以一条长链
同时只占少量渲染目标，而不是每个用过的缓冲各留一份。所有设备（含触屏）都列出这一档；
性能不足时自动降档到「AI 超分」（S 档）。

实测（macOS、Firefox 142 headless、1080p 源、同一帧 t=60s）：与 mpv 自己跑同一条链的参考帧相比，
1× 细节相关 **0.975**、2× **0.930**；55 段着色器首次编译约 **0.29s**；1080p→2× 为 **12.3 fps**
（S 档同机 22 fps）。方法、逐段数据与四联拼图见
[《WebGL2 极致档与 mpv A+A (HQ) 的逐块对齐》](upscale-webgl2-mpv-parity.zh-CN.md)。

A+A 在官方的定位是“感知质量最高”，代价是发热、风扇与耗电；官方也建议只在 2× 及以上
放大倍率使用。低分辨率或本就干净的片源上，快速档与质量档的差别可能很小。

### WebGPU 失败会被看见

WebGPU 把多数错误异步上报：校验失败、设备丢失、未捕获错误都不会抛异常。此前的后果是
在实现不完整的浏览器（例如 2026 年的 Firefox，还缺 `rgba16float` 一类的纹理能力）里，
AI 档会留一块黑画布、既不生效也不降档。现在这条路径会：用错误作用域包住管线创建、
监听设备丢失与未捕获错误、按 质量 → 快速 → 清晰化 回退，并把原因同时写进控制台和
播放详情面板的「增强错误」一行。遇到“感觉没生效”时，先看详情面板的增强模式与增强错误。

## 影视档的管线

真人片的问题不是线条，而是压缩伪影，所以影视档的顺序与 AI 超分相反：

1. **clean（源分辨率）**：5 抽头保边均值去噪去块（邻域按亮度差加权，纹理不会被抹平），同一 pass
   内按邻域亮度跨度判断色带区并向均值收敛，最后加 LSB 抖动——不做抖动的话，8-bit 输出会把这层
   刚压平的渐变重新量化成色带。
2. **EASU 放大**到画布目标（与清晰化档同一个 12 抽头核）。
3. **CAS 锐化**，强度取滑块的 0.6 倍：真人脸部比动画更容易出现光晕。

中间目标优先半浮点（WebGL2 里由 `EXT_color_buffer_float` 提供 16F 的可渲染性，Chromium 另外
也响应旧的 `EXT_color_buffer_half_float`；两者都没有、或驱动拒绝该附件时退回 8-bit）。整条链路
只需 WebGL2，不需要 WebGPU，因此手机也能开；降档阶梯是 质量 → AI 超分 → 影视 → 清晰化 → 倍率档
→ 关闭，启动失败时影视档退回清晰化。参数集中在 `client/src/util/upscale/film.ts`：
`FILM_DENOISE = 0.5`、`FILM_DEBAND = 0.6`、`FILM_SHARPEN_FACTOR = 0.6`。

clean 着色器曾把一个变量命名为 `flat`——那是 GLSL ES 3.00 的插值限定符，编译必然失败，
于是这一档在**所有浏览器**上都会启动失败并回退到清晰化（2026-09-29 修复，并加了保留字扫描
测试）。同一次修复还包括：半浮点探测漏掉 `EXT_color_buffer_float`（Firefox 只有这一个），
以及暂停/跳转时的空白画布问题，见
[画质增强诊断](upscale-diagnosis-2026-09-29.zh-CN.md)。

## 暂停、跳转与重绘

三档都只在 `requestVideoFrameCallback`（有新帧呈现）时绘制，而暂停的视频不会再产生这个回调。
因此启动、暂停、`seeked` 都会额外显式绘制一次当前帧：切档、改渲染倍率、进入全屏或窗口尺寸
稳定都会重建增强层，若此时视频是暂停的，旧实现会留下一张从未绘制过的空画布——它在 Firefox
与 Windows Chrome 上会透出底层 video，看起来就是"暂停/跳转时变回原画质"，播放中被下一帧补上
时则是"闪一两帧"。WebGL2 上下文同时使用 `preserveDrawingBuffer`，避免合成的时机把画布内容
抹掉。暂停时保留的是**超分后的画面**，与播放中一致。

渲染循环按 rVFC 元数据的 `mediaTime` 去重：同一个媒体帧被重复呈现（变速重排、seeked 之后的
下一帧回调）不会重画，省下的正是容易错过合成截止的时间。单帧绘制连续抛错三次会停下渲染并把
原因写入播放详情的「增强错误」一行——此前一次异常就会静默冻结循环，画布停住而档位仍显示开启。

## 性能与自动降档

降档阶梯为 3× → 2.5× → 2× → 1.5× → 1× → 0.75× → 0.5× → 0.25× → 关闭，一次只降一级。
判定窗口为 6 秒（重建后的第一个窗口丢弃，避免为重建自身的开销降档），判据来自三个信号：
与媒体时钟对比的**缺帧比例**（由呈现帧 `mediaTime` 的中位间隔推算片源标称节奏，短少的帧 >5%）、
实测呈现帧率低于 **18fps** 的绝对下限、以及**媒体管线自身的丢帧比例**（>8%——均匀掉帧在节奏
判据下"看起来自洽"，这一项仍然能抓到）。暂停、拖动、缓冲与后台标签页由 1 秒帧间隔检测排除在
窗口之外。视频详情的「源帧率」（同样由 `mediaTime` 中位间隔推算）与「实测帧率」「丢帧」并排，
23.976 片源在实测帧率上 23.5–24 的波动从此有对照。手机首次使用的默认锐化强度仍为 0.4。

自动档提高分辨率后，性能不足的设备靠这条阶梯兜底，而不是靠把自动值压低：
在 720p 源、2K 屏上以 2× 渲染时，清晰化档每帧写入画布约 370 万像素，
桌面独显（RTX 4060 Laptop 级别）余量很大；集显或手机若吃力会先降到 1×，
再按阶梯继续下调。

## 实测

用同一张测试图在高分辨率下渲染出真值，降采样为 720p 作为源，再分别用浏览器缩放、
旧管线（双线性 + CAS）和新管线（EASU + CAS）放大到 2K，与真值比较（本地 GPU，
ANGLE Metal）。两张源图区域（文字区、细节区）的 PSNR 与边缘能量：

| 区域 | 浏览器缩放 | 旧管线 | 新管线 |
| --- | --- | --- | --- |
| 文字区 PSNR | 21.17 dB | 21.16 dB | **21.49 dB** |
| 细节区 PSNR | 24.81 dB | 21.65 dB | **26.23 dB** |
| 细节区边缘能量 | 7.32 | 5.49 | **7.49** |

旧管线在细节区明显劣于浏览器自身的缩放（这也是“最高档仍然发糊”的来源），新管线在
两个指标上都优于两者。方向自检：新输出与真值的 PSNR 为 21.49 dB，与垂直翻转真值
只有 10.84 dB；1× 路径与源为 30.39 dB，确认没有翻转与单遍路径回归。

AI 超分两档在同一台机器上用真实 WebGPU 设备各渲染一帧 720p → 2K：均正常出画，管线
pass 数为快速档 3、质量档 4（结构见上文）。两者的观感差异随片源而定，本轮没有做
真实片源的主观对比。

线上版本（v1.1.3，与工作区一致）另做了一次无头 Chrome（真机 GPU：Apple `metal-3`）的全链路复核：
在真实房间里播放带 CORS 的 720p 直链，依次切换 清晰化 → AI 超分 → AI 超分（质量）→ 关闭。
三档都出画、切换时没有上下文冲突（每次启动都新建画布，WebGL2 与 WebGPU 不共用同一张画布），
控制台只有各档的一条 `Anime4K … drawing 965×402 from 960×400` 初始化日志，无 WebGPU 校验错误、
无降档、无回退 toast。判定方法：把 `<video>` 元素设为 `visibility: hidden` 后截图——画面仍在，
说明呈现画面的是增强画布而不是底层视频元素；档位关闭后同一位置变黑，作为对照。

## 局限

-   EASU 官方标称适用于 1×–4× 面积比（线性 1×–2×）。3× 档（9× 面积）主要面向 4K 面板
    与超采样，画质收益小于 1×→2× 段。
-   EASU 的推导假设输入无强噪声、无明显频带混叠；低码率片源的块效应不会被它消除。
-   AI 三档在 WebGPU 下最划算；没有 WebGPU 时走 WebGL2 链路，更重、更容易触发自动降档。
    运行中的渲染错误与降档原因可以在视频详情的「增强错误」与提示里看到。
-   真值对比使用合成测试图与单一 GPU，未做多设备主观对比。

## 验证范围

自动化覆盖尺寸规则（不低于源、指针设备 2× 目标、像素预算、显式档位与 3× 上限）、设置持久化（含 2.5×/3× 与
“AI 超分（质量）”，以及非法档位回退）、降档阶梯落到 0.75× 的行为，以及质量档向驱动传递
`quality` 变体、降档先从质量退回快速；着色器在本地 Chromium（真实 GPU）上做了真值对比、
方向自检与 1× 回归，Anime4K 两档也各在真实 WebGPU 设备上渲染验证。未覆盖：低端安卓与
集显的持续帧率、4K 面板的实际观感、真实片源（动漫、真人、低码率）上快速档与质量档的
主观对比。本改动为纯客户端，无数据库迁移、无新增依赖。
