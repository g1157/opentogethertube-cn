# 弹幕/画面卡顿诊断（2026-10-15）

反馈：一个人观看（直链 MP4、**画质增强开着**）时，弹幕有时一卡一卡的，视频也有、但没那么明显。
本文记录已核实的证据、排除项与待确认的机制；**结论未定之前不动渲染架构**。

## 已核实的证据

### 1. 线上遥测（v1.4.4，部署以来约 7 天、62 个播放会话）

读法见 [旧设备卡顿排查](old-device-stutter-2026-10-07.zh-CN.md) 第五节。要点：

| 指标 | 直链 | HLS | 判读 |
| --- | --- | --- | --- |
| 丢帧 / 总帧 | 307 / 568201（0.05%） | 96 / 65989（0.15%） | 媒体管线干净，**不是丢帧问题** |
| 速率写入 | ≈ 1 次 / 30 秒 | ≈ 1 次 / 6.6 秒 | 远低于"4Hz 重定时"（≈4 次/秒），候选 1 不成立 |
| 截止回退 | 0 | **15 次 / 6 个会话** | HLS 有真实的"追赶不收敛 → 硬跳"，见文末 |

### 2. 弹幕绘制成本的真实浏览器对照（本机 Chrome，有头窗口）

合成场景：30 条在屏弹幕、36px 字、20% 黑描边、800×450@dpr2 画布、60Hz 显示。

| 画法 | 每帧耗时（中位） | 帧间隔（中位） |
| --- | --- | --- |
| 现状：每帧 `strokeText + fillText` 重绘全部文字 | 0.2 ms | 16.7 ms |
| 预渲染位图 + 每帧 `drawImage` | 0.2 ms | 16.7 ms |

**结论：弹幕"每帧重新光栅化文字"在这类设备上不是瓶颈**（Chrome 的 2D 画布走 GPU 光栅，主线程只记录显示列表）。
原本计划的位图缓存方案（行业里 CommentCoreLibrary 等的常规做法）在测量后收益≈0，未实施。
另注意：无头模式 + `getImageData` 强制刷新的测法会系统性失真（位图反而测出 10ms），只有**有头 + rAF** 的测量可信。

### 3. 弹幕流畅度等于页面帧率（机制判断，待用面板读数确认）

弹幕画布由 rAF 驱动（`DanmakuLayer.vue` 的 `schedule()/onFrame()`），**页面帧率是多少，滚动弹幕就是多少 fps**，
与媒体管线自己的出帧率无关。超分开着时画面由 rVFC 驱动的画布呈现，每视频帧的主线程/GPU 工作一旦挤占帧预算，
页面帧率会向片源的出帧节奏（24fps 左右）塌陷：此时弹幕变成"24fps 的文字"，一卡一卡非常明显；而 24fps 片源本身
看起来就是那个样子，视频反而"顿得少"。——这一条解释了"弹幕顿得多、视频也有"的形态，但**尚未在真机上取到页面帧率读数**。

## 新增读数：播放详情里的「页面帧率」

`player-stats.ts` 新增 rAF 采样的「页面帧率」（1 秒窗口 × 最近 4 个窗口平均，暂停时显示「—」），与 rVFC 的
「实测帧率」并排。判读表：

| 页面帧率 | 实测帧率 | 结论 |
| --- | --- | --- |
| ≈ 刷新率（60/120） | ≈ 刷新率 | 帧预算没问题；弹幕若仍顿，查时钟锚定/单调性等渲染之外的原因 |
| **明显低于刷新率、接近片源节奏（24–30）** | 正常或同低 | 整页帧预算被每帧工作占用（超分等）→ 弹幕首当其冲；修整页成本或让弹幕离开主线程 |
| 接近刷新率 | 明显低 | 媒体管线自身跟不上，与弹幕/覆盖层无关 |

## 方向选择（待定，未动代码）

-   **A. 弹幕改由合成器驱动**：每条弹幕用 DOM + CSS `transform` 动画（`will-change: transform`），主线程卡顿时
    由合成器继续推进，弹幕保持顺滑。产业做法（B 站及多数网页弹幕库为 DOM 或 DOM/画布双层）。改动大：渲染层重写、
    低端机上层数与内存上限需要真机验证；引擎（避让/测量/调度）可以复用。
-   **B. 压缩超分的每帧成本 / 加快降档反应**：整页帧率上去了，弹幕自然好转；与
    [改进方向](improvement-directions.zh-CN.md) 1.3（GPU 时间驱动、快攻慢释）同向，收益面更广，但同样需要真机标定。

建议：先用「页面帧率」在真机上确认属于哪一行，再在同一次对照里比较关/开超分的页面帧率；A 与 B 的投资回报取决于
这一步的结果（若关超分后页面帧率仍低，说明瓶颈不在超分）。

## 顺带发现：HLS 截止回退（另一条线）

6 个 HLS 会话里出现 15 次 `deadline_seeks`（速率弯曲 8–30 秒仍不收敛 → 硬跳一次）。每次都是可见的"顿/跳"，
与本文反馈的视频卡顿形态不冲突但独立。最小改点（见旧设备排查文档候选 2）：连续截止后进入更长的"只 seek"冷却、
或对低性能客户端直接先 seek 不再长弯——落地前需要先有线上的对照数据（该计数已在遥测里）。

## 复现与测量方法（可复用）

1. 合成对照：本地自建 HTML（30 条弹幕、36px、dpr2、`requestAnimationFrame` 逐帧计时），分别跑"每帧文字重绘"
   与"预渲染位图"，报告每帧耗时与帧间隔的中位数/p95——**必须在有头窗口里跑**。
2. 真机读数：播放详情（右键画面或 播放器设置 → 更多设置 → 视频详情）看「页面帧率 / 实测帧率 / 丢帧」；
   对照开/关画质增强各 60 秒。
3. 线上判读：服务器上 `curl -H "apikey: $KEY" 127.0.0.1:8090/api/status/metrics | grep ott_playback`（读法同旧设备文档）。
